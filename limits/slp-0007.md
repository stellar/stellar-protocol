## Simple Summary

This proposal raises five ledger-wide Soroban limits to support: disk read entries and write entries (1,000 to 2,000), write bytes (286,720 to 297,000), transaction size (266,240 to 864,000), and dependent transaction clusters (2 to 4). This is a proactive change to support increased throughput. Fees for Soroban resources are also cut in half, rounded down to the nearest integer.

## Motivation

Classic operations per ledger are currently limited to 1,000. However, the current Soroban limits are too low to fit an equivalent number of SAC transfers. Similarly, the current limits are too low to support a modeled Soroswap invocation at 250 transactions per ledger (TPL). This proposal raises the limits to support these two scenarios.

### Goals Alignment

The fee decreases align with the goal that "The Stellar network should run at scale and at low cost to all participants of the network." This goal also helps motivate the increase in ledger limits, as does the goal that "The Stellar network should make it easy for developers of Stellar projects to create highly usable products."

## Impact Assessment

In addition to the considerations below, the lowering of fees may incentivize higher usage of Soroban, which could amplify the impact described below.

### Core

Ledger close time may go up due to the increase in: disk read entries, disk write entries, and disk write bytes. It is also expected that the increase in write bytes can increase the speed of ledger growth. The increase in the transaction byte size limit is expected to increase both network bandwidth and the size of the history archive. Increasing dependent transaction clusters to four may increase the latency for non-apply work that happens while applying Soroban transactions. Notably, four is the suggested number of "physical" cores at this time.

### Downstream

The ledger-close meta size is expected to increase through both the increase in write bytes and the increase in transaction byte size. Note that the increase in write bytes is small, so most of the impact is likely to come from the increase in transaction byte size.

## Justification of the Proposed Numbers

The model SAC transaction (a simple G-to-G transfer of an `AssetCode4`) reads two ledger entries (the source and destination trustlines), writes two ledger entries (the source and destination trustlines), and uses 864 bytes.

So, to fit 1,000 such transactions in a ledger, we need 2,000 read entries, 2,000 write entries, and 864,000 bytes. The disk write bytes limit is increased to support 250 TPL of a model Soroswap invocation that uses 1,188 write bytes. The dependent transaction clusters limit is increased since it allows better work parallelization in the best case. Overall, this proposal supports the [foundation's strategy](https://stellar.org/foundation/strategy) goal to "Increase Mainnet transactions per second across the stack."

## Technical Evaluation

### Core apply-side

The ledger limits are evaluated using the `apply-load` script. All benchmarks are run on a `c5d.2xlarge` AWS instance (8 vCPUs, 16 GiB RAM) on `stellar-core 28.0.1-3508.947aad841.jammy-perftests` over 200 synthetic ledger closes. The benchmarked scenarios are intended to cover the edge cases of a small number of large transactions and a large number of small transactions. In some of the cases, the ledger-wide transaction byte size limit[^1] is raised to support transaction generation with the specified configuration at the desired TPL. The goal is that the scenarios cover high utilization (>98%) of resources[^2] while keeping the average ledger close time under 300 milliseconds (the target established in SLP-0004). All of the benchmarked scenarios meet this goal.

[^1]: Transaction byte size does not have a big impact on ledger close time, so it is allowed to drift upward to make benchmarking easier (e.g., if the transaction size that hits the other limits is too big to fit at the desired TPL, the byte limit could be raised).
[^2]: Utilization for contract event bytes is not considered since it does not have a substantial effect on ledger close time. Disk reads are not held to the same utilization requirement for the same reason as in SLP-0004 (the benchmark utilizes restoration entries, which can be overly pessimistic).

#### Evaluation of current limits

As in SLP-0004, the current ledger limits are re-evaluated. This helps capture any differences in Soroban resource accounting or benchmarking. Three scenarios are benchmarked with a limit of 10,000 IOPS.

12 is taken from the prior SLP-0004 evaluation, and 492 and 494 straddle the prior 493 since the benchmark script only generates multiples of the number of dependent clusters.

#### Evaluation of proposed limits

Two TPL values are evaluated with three cluster configurations. The cluster configurations are with 1, 2, and 4 dependent clusters. This is intended to cover the edge cases for resource distribution. The four-cluster configuration uses the most instructions (ledger instruction capacity scales with the number of clusters) while one cluster has the worst parallelization for non-instruction resources. The TPL used are 12 (the smallest multiple of four showing good utilization) and 2,000 (the maximum possible TPL). Due to the aforementioned issue with read entries, these benchmarks are run without read entries.

### Core overlay

To evaluate the impact of the proposed changes on the overlay, the `slp_eval.sh` script from supercluster is used. At a high level, the test checks that ledger close time is not too adversely impacted by the proposed changes. The specific SLA is that the p75 ledger age is within 20% of the target block time and that the p99 ledger age is under twice the target block time. Six load profiles under two topologies are tested.

Soroban load profiles for current network limits
* SAC transfer: 62 TPS
* OZ token transfer: 60 TPS
* Soroswap swap: 29 TPS

Soroban load profiles for target network limits
* SAC transfer: 200 TPS
* OZ token transfer: 180 TPS
* Soroswap swap: 50 TPS

For all load profiles, the classic transaction load is set to 200 payment TPS. In the test, apply time is simulated to be ~600 milliseconds per ledger.

Both topologies are based on a subset of a recent snapshot of mainnet and are configured to use the current 10 tier-1 organizations. Connectivity between the tier-1s is somewhat sparse, with an average of 5.73 direct neighbors.
* Sparse topology: 70 additional nodes with an average tier-1 fanout of 12.3
* Dense topology: 247 additional nodes with an average tier-1 fanout of 28.1

This testing was done on `stellar-core:28.0.2-3602.30eb64184.noble-do-not-use-in-prd-perftests` ([stellar-core commit](https://github.com/stellar/stellar-core/commit/30eb64184)), which is one commit on top of 28.0.1 to have the simulated Soroban load padded and wrapped in a fee-bump envelope. The corresponding supercluster commit to support the changes is [a1fb5b10](https://github.com/stellar/supercluster/commit/a1fb5b10ec28b2a3de39ed4ea471519227ad0478).

## Security Concerns

Most of these changes have no material new security concerns since the resource accounting and metering semantics are unchanged. However, decreasing the fees and increasing the limits allows more spam. The evaluations above suggest that the network can handle the increased load. The increase in clusters does present a potential issue since it could lead to increased contention for non-apply work (in the worst case, during the Soroban apply phase, all physical cores of the target SKU could be occupied with Soroban work). The expected impact would be an increase in latency for non-apply work during the Soroban apply phase. This risk is partially mitigated by apply being relatively infrequent (~300 milliseconds every five seconds).
