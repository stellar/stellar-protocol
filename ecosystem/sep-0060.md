## Simple Summary

This proposal describes an improvement to common connection patterns between wallets and applications. Adopting an event driven connection protocol improves the user experience and avoids contention over global variables shared across many wallets. A connection standard will also allow new wallets to announce themselves for connection without the need for source code changes in connector libraries.

A wallet tells the page it is available by dispatching a `window` event that carries a small description of the wallet and a [SEP-43] provider object. A dapp listens for those events in order to establish a connection and can also announce itslef to the wallet. Wallets never need to share a global variable, any number of wallets can coexist on one page, and the same mechanism works for browser extensions, wallet apps with a built-in browser, web page wallets, and automation hosts.

## Dependencies

- [SEP-43]: Standard Web Wallet API Interface. The announced `provider` MUST implement the SEP-43 interface. This proposal does not change SEP-43.

## Motivation

SEP-43 standardizes what a dapp can ask a wallet to do, but not how a dapp finds the wallet. Wallets have established teir own patterns for connections, which has created the need for "glue" libraries like [Stellar Wallets Kit](https://github.com/Creit-Tech/Stellar-Wallets-Kit/) to absorb the differences. While this helps application developers abstract away connection patterns, it requires changes for any new wallet to be included, and suffers from a few pitfalls:

- Most extension wallets install an object under a wallet-specific global (`window.rabet`, `window.hanaWallet`, `window.xBullSDK`). One widely used extension installs nothing on `window` and instead answers a private `postMessage` protocol from its companion npm package.
- Freighter Mobile's in-app browser injects an identifying object at window.stellar — { provider, platform, version } — plus a FreighterMobile/<version> User-Agent marker, so libraries can tell they are running inside it (freighter-mobile #314 (https://github.com/stellar/freighter-mobile/pull/314)). The object carries no methods; it is a beacon for detection only, and dapp interaction still leaves over WalletConnect. Stellar Wallets Kit reads that beacon from two different modules: FreighterModule.isAvailable() returns false when it sees it, and WalletConnectModule.isPlatformWrapper() returns true by matching it against a hardcoded list of { provider, platform } pairs. The wrapper signal is therefore attached to the transport rather than to the wallet, and it exists only if the application configured WalletConnect — the module requires a projectId, so a site that never supplied one registers nothing that claims to be the wrapper. The picker then renders Freighter as unavailable, and a click opens its install page: "Install Freighter", shown to a user already inside Freighter Mobile.
- Scopuly solves the same problem again a different way. It injects window.scopuly carrying its own platform field, and ScopulyModule.isPlatformWrapper() checks window.scopuly?.platform === "mobile". Because a global cannot say when it is ready, the wallet also dispatches a private scopuly#initialized event, which its module waits on for up to 800ms before deciding the wallet is absent. Two wallets have now built two incompatible globals, two platform fields meaning the same thing, and one hand-rolled readiness event between them — and each arrangement needed its own module in the kit.
- [freighter-mobile #1001](https://github.com/stellar/freighter-mobile/pull/1001) replaces that WalletConnect round trip with a bridge injected into the WebView. Without a discovery standard it needs its own transport, its own SDK, and a claim on `window.stellar` that any other script can collide with.
- [Stellar-Wallets-Kit #111](https://github.com/Creit-Tech/Stellar-Wallets-Kit/issues/111) asks how a host with browser control can offer wallet interactions at all. Today the only option is to impersonate an existing provider's scheme.
- Modules poll for a global object written by an extension, this can cause race conditions between the wallet and the application.

## Abstract

This proposal defines two DOM events and two data models.

A wallet dispatches `sep0060:announceProvider` on `window` when it is ready to serve requests. The event's `detail` is an object that describes the wallet and provides a SEP-43 interface.

An application adds a listener for `sep0060:announceProvider` and then dispatches `sep0060:requestProvider`, which wallets answer by announcing again. If the wallet loaded first its initial announcement is missed but the request brings a new one; if the application loaded first its request is missed but the wallet's later announcement is caught by the application's persistent listener.

Which wallet to connect to remains the user's choice, with one exception that requires no claim by a wallet: when the handshake settles and exactly one provider has announced, a library may connect to it directly. Inside a mobile wallet's in-app browser that is always the case, because no other wallet can announce there.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119].

### Definitions

- **Wallet Provider** (or **Wallet**): software that manages Stellar keys and exposes a SEP-43 interface to web pages.
- **Dapp/Application**: a web page that uses a Wallet Provider through its SEP-43 interface.
- **Discovery Library**: code that an application uses to find and select Wallet Providers, such as Stellar Wallets Kit. Requirements placed on applications apply equally to Discovery Libraries acting on their behalf.

### Provider Info

Each announcement carries a `StellarProviderInfo`. All required fields MUST be present. Unknown properties MAY be present and MUST be ignored by applications that do not recognize them.

```typescript
interface StellarProviderInfo {
  uuid: string;
  name: string;
  icon: string;
  rdns: string;
  version?: string;
  platform?: "extension" | "mobile" | "desktop" | "web" | "agent";
}
```

- uuid: A UUIDv4 generated by the Wallet once per page session. Distinguishes two announcements from providers that otherwise look alike and lets a Dapp detect duplicate or replayed announcements.
- name: Human-readable wallet name for display.
- icon: A data: URI image. MUST be a data URI (RFC 2397). SHOULD be square and at least 96x96 pixels. SVG, PNG, and WebP are RECOMMENDED. Dapps MUST render it with an <img> element and MUST NOT inline SVG markup into the DOM.
- rdns: A reverse-DNS identifier that is stable across sessions and versions, e.g. "app.freighter" or "com.example.wallet". The domain part SHOULD be a domain the Wallet's publisher controls. This value is self-attested. This value MUST be a valid RFC 1034 domain name and the dns part SHOULD BE an active domain controlled by the provider.
- version: Version of the Wallet software, for diagnostics.
- platform: How the Wallet is delivered. Lets a Dapp adapt copy or layout without user-agent sniffing. Self-attested and advisory only: an application MUST NOT derive host identity, authority, or provider selection from this value.

### Provider Detail

The announced value pairs the info with the provider object.

```typescript
interface StellarProviderDetail {
  info: StellarProviderInfo;
  provider: StellarProvider;
}
```

`provider` MUST implement the SEP-43 interface, including its error shape. [SEP-43] is authoritative for the method signatures.

The Wallet SHOULD call `Object.freeze()` on `detail` and on `info` before dispatching. Freezing `provider` is RECOMMENDED when the Wallet does not need to mutate it after announcement.

### Events

Two events are defined. Both MUST be dispatched with `window.dispatchEvent` and observed with `window.addEventListener`.

```typescript
/** Dispatched by a Wallet. */
interface StellarAnnounceProviderEvent extends CustomEvent {
  type: "sep0060:announceProvider";
  detail: StellarProviderDetail;
}

/** Dispatched by a Dapp/Application. */
interface StellarRequestProviderEvent extends Event {
  type: "sep0060:requestProvider";
}
```

#### Wallet requirements

1. When its in-page code is ready to serve requests, the Wallet MUST dispatch `sep0060:announceProvider` with a `StellarProviderDetail` as the `detail`.
2. The Wallet MUST listen for `sep0060:requestProvider` and MUST respond to every such event by announcing again with the same `detail`.
3. The Wallet MUST use the same `uuid` for every announcement it makes during one page session. A new document is a new session.
4. The Wallet SHOULD announce in the top-level browsing context. Extensions that inject into iframes MAY announce in each frame, and each frame is then an independent discovery scope. Hosts that embed pages SHOULD announce only in the top-level document.

#### Dapp/Application requirements

1. The application MUST add its `sep0060:announceProvider` listener before it dispatches `sep0060:requestProvider`.
2. The application MUST NOT remove that listener for the lifetime of the page. Wallets may become ready after the application's code has run, and the application's UI SHOULD react to late announcements.
3. The application SHOULD deduplicate announcements by `uuid`.
4. The application MAY dispatch `sep0060:requestProvider` again at any time, for example when the user opens a wallet picker.
5. The application MUST NOT treat any field of `info` as a security boundary.
6. The application MUST NOT use any field of `info` to decide which provider to connect to. See [Selecting a provider](#selecting-a-provider) for the one case in which an application MAY connect without asking the user.

#### Ordering

The handshake is symmetric, so correctness does not depend on load order and no timeouts are required. A Dapp that wants to render a "no wallets found" state SHOULD wait a short grace period after its request before doing so, and SHOULD replace that state if an announcement arrives later.

### Selecting a provider

Which provider an application uses is the user's choice, expressed through the application's own interface. This proposal defines one case in which that choice may be made without asking, and it rests on how many providers announced rather than on anything a provider claims about itself.

After dispatching `sep0060:requestProvider`, an application SHOULD allow a short settle period for announcements to arrive. When that period has elapsed and exactly one provider has announced, a Discovery Library MAY connect to it without presenting a picker. When two or more have announced, the application MUST let the user choose. The settle period is the grace period described under [Ordering](#ordering): an application deciding to render "no wallets found" and an application deciding to connect to a lone provider are making the same decision at the same moment. Its length is not normative, and implementations use a few hundred milliseconds.

This is what replaces today's hardcoded lists of wrapping providers, and it covers the in-app browser case without a declared flag. A mobile wallet's in-app browser or a desktop wallet's embedded web view is the only Wallet that can announce inside its own web view, so the count is one and the user connects with no extra step. A Host in that position SHOULD inject its announcer before any page script runs, both so that its announcement is never missed and so that the application's settle period can be short.

Whatever the count, an application MUST NOT present install or open affordances for a Wallet that has announced. A Wallet that announced is by definition already present. This is what removes the "Install Freighter" button shown to a user already inside Freighter Mobile, and it follows from the announcement alone rather than from anything the wallet claims or from which transport the library happens to have configured.

An application MAY remember the `rdns` of the provider the user chose and prefer it on a later visit. That preference is the user's own rather than a claim by a Wallet, and is the RECOMMENDED way to avoid repeated prompts.

### Hosts that are not extensions

The mechanism is the same for every kind of host; only the delivery differs.

- A **browser extension** runs the announcer from a content script in the page's main context.
- A **mobile or desktop wallet with an embedded browser** injects it before content loads and bridges the provider's methods to native code. The object the page sees is a SEP-43 provider like any other; the transport behind it is the Wallet's concern.
- An **automation or agent host** injects it as an initialization script on every new document and bridges the provider's methods to a process outside the page that holds the keys and enforces signing policy. Such Hosts SHOULD set `platform: "agent"`.

In all cases the page never holds key material. An announced provider is an interface to a signer, not the signer itself.

### Backwards compatibility

This proposal adds a discovery channel, existing solutions can still be supported.

- Wallets MAY keep their existing globals, `postMessage` protocols, or companion packages, and SHOULD announce in addition to, not instead of, that legacy surface until application adoption is broad.
- Discovery Libraries SHOULD prefer an announced provider over a legacy detection path for the same wallet. To avoid listing one wallet twice, libraries SHOULD map known `rdns` values to their legacy module identifiers and suppress the legacy entry when the announced one is present.
- Wallets that publish an identifying object at `window.stellar` so libraries can detect their in-app browser SHOULD migrate to announcing, and libraries SHOULD drop the special case once the announcing version is widely deployed. A Discovery Library with an existing wrapper hook, such as Stellar Wallets Kit's per-module `isPlatformWrapper()`, can satisfy it from the announced count rather than from a hardcoded list of `{ provider, platform }` pairs, so the behavior it drives survives the migration and stops depending on whether the application configured a particular transport. This proposal does not reserve or define `window.stellar`.
- Wallets SHOULD publish their `rdns` value in their developer documentation so library maintainers can build that mapping.

## Design Rationale

### Events instead of a shared global

A `window.someNamespace` is global and can be mutated by any code that has access to the window. This incentivices wallets to delay their initialization and compete for the namespace. Events are not owned, removing the possibility of any clashes and providing the delivery of all announcements.

### One channel among several

Announcement-based discovery only reaches wallets with code in the page, so Discovery Libraries will still need other paths for other provider types, like hardware wallets.

### The info fields

`uuid` is a session identity, letting a Dapp tell announcements apart and spot
one replayed or forged with copied fields. `rdns` is a stable identity, letting
a Dapp remember a preferred wallet across sessions and letting libraries map
announced providers onto legacy entries. `platform` replaces the user-agent
markers a mobile wallet relies on today; it informs copy and layout only, and
nothing normative depends on it.

### Alternatives considered

- **A declared `wrapsPage` flag.** Replaces a hardcoded list of wrapping
  providers with a self-attested one and rewards every wallet for setting it;
  see above. A Discovery Library that wants wrapper semantics beyond what the
  count gives it can key them off its own registry of known `rdns` values,
  leaving the attestation with the library that reviews it rather than with the
  wallet that benefits from it.
- **Standardize `window.stellar`.** Fixes the data model but not the ownership, and
  is still open to collisions from any script on the page.
- **User-Agent markers.** Work only for hosts that control the browser, are
  invisible to page code without server help, and need an addition per wallet.
- **Keep absorbing the differences in a library.** The status quo, which needs
  a change to Stellar Wallets Kit for every new wallet and provider type.

## Security Concerns

**Announcement grants no authority.** Discovering a provider gives an application nothing it did not already have. Every SEP-43 method still runs through the Wallet's own approval flow, and Wallets MUST NOT treat a Dapp's request event as consent for anything.

**Everything in `info` is self-attested.** The announcing code runs in the page context and can claim any `name`, `icon`, `rdns`, or `platform` value. Applications MUST NOT use these fields for authentication, authorization, or security gating. No field of `info` participates in provider selection, so impersonated metadata cannot win a default connection; it can only mislead a user who is already being asked to choose. Applications SHOULD treat two announcements sharing a `uuid` but carrying different `provider` objects as suspect.

**Address ownership.** `getAddress()` is not proof that the user controls the address returned. Applications that need proof MUST obtain and verify a signature, using `signMessage` per [SEP-53] or a signed transaction.

**Object integrity.** Wallets SHOULD freeze `detail` and `info`, and are RECOMMENDED to freeze `provider`. Applications SHOULD capture the `provider` reference at announcement time and call through it rather than re-reading it from a shared location. Because SVG can contain scripts, Applications MUST render `icon` via an `<img>` element and MUST NOT insert SVG source into the document.

**Iframes.** A provider announced inside an iframe is scoped to that frame. Hosts that embed pages SHOULD announce only in the top-level document, and a provider whose transport authenticates the calling document SHOULD refuse requests from frames it did not activate. Applications SHOULD NOT rely on a provider announced in a cross-origin iframe they do not control.

**Fingerprinting.** Announcing on every page reveals which wallets a user has installed. Wallets MAY defer their initial announcement until they observe a `sep0060:requestProvider` event, and MAY require user consent before announcing on an origin, accepting that applications which never dispatch the request event will not discover them.

**Agent and automation hosts.** A host that signs on policy or or demand SHOULD restrict announced providers to an allowlist of origins, SHOULD simulate transactions before signing, and SHOULD default to test networks. These are host concerns outside this specification, noted because the specification makes such hosts easy to build.

## Reference Implementation

A Wallet announces once when ready and again on every request:

```typescript
function announceStellarProvider(provider: StellarProvider): void {
  const detail: StellarProviderDetail = Object.freeze({
    info: Object.freeze({
      uuid: crypto.randomUUID(),
      name: "Example Wallet",
      icon: "data:image/svg+xml;base64,PHN2ZyB4bWxucz0i...",
      rdns: "com.example.wallet",
      version: "1.4.0",
      platform: "extension" as const,
    }),
    provider,
  });

  const announce = (): void => {
    window.dispatchEvent(
      new CustomEvent("sep0060:announceProvider", { detail })
    );
  };

  window.addEventListener("sep0060:requestProvider", announce);
  announce();
}
```

An in-app browser or agent host calls the same function from its injected
bootstrap, with `platform` set accordingly. It asserts nothing further about
being the host; inside its own web view it is the only announcer.

An application listens first, then requests:

```typescript
const providers = new Map<string, StellarProviderDetail>();

window.addEventListener("sep0060:announceProvider", (event) => {
  const { detail } = event as StellarAnnounceProviderEvent;
  if (!detail?.info?.uuid || !detail.provider) return;
  if (providers.has(detail.info.uuid)) return;
  providers.set(detail.info.uuid, detail);
  renderWalletPicker([...providers.values()]);
});

window.dispatchEvent(new Event("sep0060:requestProvider"));

// Once the handshake has settled, a lone provider needs no picker. Inside a
// wallet's in-app browser that is always the case; on a desktop with two
// extensions installed it never is.
const SETTLE_MS = 500;

setTimeout(() => {
  const found = [...providers.values()];
  if (found.length === 1) connectTo(found[0]);
  else if (found.length === 0) renderNoWalletsFound();
}, SETTLE_MS);
```

A Discovery Library needs one adapter for all announced providers rather than
one module per wallet: it registers an adapter on each announcement, forwards
the SEP-43 methods to `detail.provider`, and takes its identity and display
fields from `detail.info`.
