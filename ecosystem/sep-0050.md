## Summary

This proposal defines a standard contract interface for non-fungible tokens.
The interface is a similar to [ERC721](https://eips.ethereum.org/EIPS/eip-721),
but factors in the differences between Ethereum and Stellar.

## Motivation

A non-fungible asset (NFT) is a fundamental concept on blockchains,
representing unique and indivisible digital assets. While most blockchain
ecosystems have established standards for NFTs, such as
[ERC-721](https://eips.ethereum.org/EIPS/eip-721) and
[ERC-1155](https://eips.ethereum.org/EIPS/eip-1155) in Ethereum, the Stellar
ecosystem lacks a standardized interface for NFTs. This absence may lead to
fragmentation, making it difficult to ensure interoperability between different
NFT contracts and applications.

NFTs already exist on Stellar as assets with unique metadata, as described in
[SEP-39](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0039.md),
and a Stellar Asset Contract (SAC) can be deployed for them. This SEP defines
another approach, where an NFT is a smart contract. Both can be used side by
side, and a smart contract can also work with a SEP-39 asset through its SAC.

This proposal defines a non-fungible token interface that provides core NFT
functionality, including ownership management, transfers, and approvals,
without enforcing opinionated behaviors beyond the standard expectations for
NFTs. By establishing this interface, NFT contracts can interact seamlessly
with other contracts and applications that support the standard, ensuring
broader usability and compatibility within the Stellar network.

## Interface

NFTs can have diverse use cases, and there is no universal `token_id` format
that fits all scenarios. Some implementations may use sequential numbers, while
others may opt for UUIDs or hashes. To accommodate this variability, this
interface remains agnostic to the specific `token_id` format, defining it as a
generic `TokenID` type, which should be an unsigned integer.

Additionally, since a single account cannot hold more tokens than the total
supply of `TokenIDs`, we introduce a `Balance` type. In most cases, `Balance`
should use the same type as `TokenID` for consistency.

Both types are free, but we recommend `u32` for `TokenID` and `Balance`. Some
wallets and integrations only support `u32` token ids, so it is the minimum an
integration should support.

```rust
/// The `NonFungibleToken` trait defines the core functionality for non-fungible
/// tokens. It provides a standard interface for managing
/// transfers and approvals associated with non-fungible tokens.
pub trait NonFungibleToken {
    /// Returns the number of tokens in `owner`'s account.
    ///
    /// # Arguments
    ///
    /// * `e` - Access to the Soroban environment.
    /// * `owner` - Account of the token's owner.
    fn balance(e: &Env, owner: Address) -> Balance;

    /// Returns the address of the owner of the given `token_id`.
    ///
    /// # Arguments
    ///
    /// * `e` - Access to the Soroban environment.
    /// * `token_id` - Token id as a number.
    ///
    /// # Notes
    ///
    /// If the token does not exist, this function is expected to panic.
    fn owner_of(e: &Env, token_id: TokenID) -> Address;

    /// Transfers `token_id` token from `from` to `to`.
    ///
    /// WARNING: Note that the caller is responsible to confirm that the
    /// recipient is capable of receiving the `Non-Fungible` or else the NFT
    /// may be permanently lost.
    ///
    /// # Arguments
    ///
    /// * `e` - Access to the Soroban environment.
    /// * `from` - Account of the sender.
    /// * `to` - Account of the recipient.
    /// * `token_id` - Token id as a number.
    ///
    /// # Events
    ///
    /// * topics - `["transfer", from: Address, to: Address]`
    /// * data - `[token_id: TokenID]`
    fn transfer(e: &Env, from: Address, to: Address, token_id: TokenID);

    /// Transfers `token_id` token from `from` to `to` by using `spender`s
    /// approval.
    ///
    /// Unlike `transfer()`, which is used when the token owner initiates the transfer,
    /// `transfer_from()` allows an approved third party (`spender`) to transfer the token
    /// on behalf of the owner. This function includes an on-chain check to verify that
    /// `spender` has the necessary approval.
    ///
    /// WARNING: Note that the caller is responsible to confirm that the
    /// recipient is capable of receiving the `Non-Fungible` or else the NFT
    /// may be permanently lost.
    ///
    /// # Arguments
    ///
    /// * `e` - Access to the Soroban environment.
    /// * `spender` - The address authorizing the transfer.
    /// * `from` - Account of the sender.
    /// * `to` - Account of the recipient.
    /// * `token_id` - Token id as a number.
    ///
    /// # Events
    ///
    /// * topics - `["transfer", from: Address, to: Address]`
    /// * data - `[token_id: TokenID]`
    fn transfer_from(e: &Env, spender: Address, from: Address, to: Address, token_id: TokenID);

    /// Gives permission to `approved` to transfer `token_id` token to another
    /// account. The approval is cleared when the token is transferred.
    ///
    /// Only a single account can be approved at a time for a `token_id`.
    /// To remove an approval, the approver can approve their own address,
    /// effectively removing the previous approved address.
    ///
    /// # Arguments
    ///
    /// * `e` - Access to Soroban environment.
    /// * `approver` - The address of the approver (should be `owner` or `operator`).
    /// * `approved` - The address receiving the approval.
    /// * `token_id` - Token id as a number.
    /// * `live_until_ledger` - The ledger number at which the allowance
    ///   expires.
    ///
    /// # Events
    ///
    /// * topics - `["approve", from: Address, to: Address]`
    /// * data - `[token_id: TokenID, live_until_ledger: u32]`
    fn approve(e: &Env, approver: Address, approved: Address, token_id: TokenID, live_until_ledger: u32);

    /// Approve or remove `operator` as an operator for the owner.
    ///
    /// Operators can call `transfer_from()` for any token held by `owner`,
    /// and call `approve()` on behalf of `owner`.
    ///
    /// # Arguments
    ///
    /// * `e` - Access to Soroban environment.
    /// * `owner` - The address holding the tokens.
    /// * `operator` - Account to add to the set of authorized operators.
    /// * `live_until_ledger` - The ledger number at which the allowance
    ///   expires. If `live_until_ledger` is `0`, the approval is revoked.
    ///
    /// # Events
    ///
    /// * topics - `["approve_for_all", from: Address]`
    /// * data - `[operator: Address, live_until_ledger: u32]`
    fn approve_for_all(
        e: &Env,
        owner: Address,
        operator: Address,
        live_until_ledger: u32,
    );

    /// Returns the account approved for `token_id` token.
    ///
    /// # Arguments
    ///
    /// * `e` - Access to the Soroban environment.
    /// * `token_id` - Token id as a number.
    ///
    /// # Notes
		///
		/// If the token does not exist, this function is expected to panic.
    fn get_approved(e: &Env, token_id: TokenID) -> Option<Address>;

    /// Returns whether the `operator` is allowed to manage all the assets of
    /// `owner`.
    ///
    /// # Arguments
    ///
    /// * `e` - Access to the Soroban environment.
    /// * `owner` - Account of the token's owner.
    /// * `operator` - Account to be checked.
    fn is_approved_for_all(e: &Env, owner: Address, operator: Address) -> bool;

    /// Returns the token collection name.
    ///
    /// # Arguments
    ///
    /// * `e` - Access to the Soroban environment.
    fn name(e: &Env) -> String;

    /// Returns the token collection symbol.
    ///
    /// # Arguments
    ///
    /// * `e` - Access to the Soroban environment.
    fn symbol(e: &Env) -> String;

    /// Returns the Uniform Resource Identifier (URI) for `token_id` token.
    ///
    /// # Arguments
    ///
    /// * `e` - Access to the Soroban environment.
    /// * `token_id` - Token id as a number.
    ///
    /// # Notes
		///
		/// If the token does not exist, this function is expected to panic.
    fn token_uri(e: &Env, token_id: TokenID) -> String;
}
```

## Events

### Transfer Event

The transfer event is emitted when an NFT is transferred from one address to
another.

**Topics:**

- `Symbol` with value `"transfer"`
- `Address`: the address holding the token that was transferred.
- `Address`: the address that received the token.

**Data:**

- `TokenID`: the identifier of the transferred token.

### Approve Event

The "approve" event is emitted when an owner grants another address permission
to manage a specific token.

**Topics:**

- `Symbol` with value `"approve"`
- `Address`: the owner of the token.
- `TokenID`: the identifier of the token.

**Data:**

- `Address`: the approved address.
- `u32`: the expiration ledger.

### Approve for All Event

The "approve for all event" is emitted when an owner grants or revokes
permission for an operator to manage all of their NFTs.

**Topics:**

- `Symbol` with value `"approve_for_all"`
- `Address`: the owner of the tokens.

**Data:**

- `Address`: the operator receiving or losing permission.
- `u32`: the expiration ledger. If `0`, the approval is revoked.

### Mint Event

The `mint` event is emitted when a token is minted.

The event has topics:

- `Symbol` with value `"mint"`
- `Address`: the address to hold the newly minted token.

The event has data:

- `TokenID` the identifier of the minted token.

### Metadata Event

The `metadata` event is emitted when the metadata of a token changes after
mint, that is, when the output of `token_uri(token_id)` changes, or when the
contract changes the content it points to. It lets clients that cache the
metadata of a dynamic NFT know when to fetch it again. A contract whose
metadata never changes does not emit it. The event is inspired by
`MetadataUpdate` in [ERC-4906](https://eips.ethereum.org/EIPS/eip-4906).

The event has topics:

- `Symbol` with value `"metadata"`

The event has data:

- `TokenID`: the identifier of the token whose metadata changed.

### Batch Metadata Event

The `batch_metadata` event is emitted when the metadata of a range of tokens
changes at once, for example when a contract that generates its metadata
changes how it draws every token. It stands for one `metadata` event per token
of the range. The event is inspired by `BatchMetadataUpdate` in
[ERC-4906](https://eips.ethereum.org/EIPS/eip-4906).

The event has topics:

- `Symbol` with value `"batch_metadata"`

The event has data:

- `TokenID`: the identifier of the first token of the range.
- `TokenID`: the identifier of the last token of the range, included.

## Notes on `mint()`:

- Minting functionality is typically implemented as an internal function (see
  [[OpenZeppelin Contracts](https://github.com/OpenZeppelin/openzeppelin-contracts)](https://github.com/OpenZeppelin/openzeppelin-contracts))
  to emphasize that the standard does not impose any specific minting logic.
  This allows developers to adopt an approach that best suits their contract’s
  requirements. In this SEP, we do not specify any standards for `minting`
  tokens.

## Notes on `safeTransferFrom`:

- In ERC-721, `safeTransferFrom` and `onERC721Received` exist to prevent the
  loss of NFTs when transferring them to a smart contract that does not support
  NFT-related operations.
- However, this approach comes with significant overhead:
  - An additional on-chain transaction is required for verification.
  - The receiving contract must implement `onERC721Received`.
- A more efficient alternative is the
  [`[permit](https://eips.ethereum.org/EIPS/eip-2612)`](https://eips.ethereum.org/EIPS/eip-2612)
  mechanism (EIP-2612), which leverages off-chain signatures to authorize the
  recipient to claim the tokens, reducing on-chain transactions from two to
  one.

## Notes on `permit`:

`safeTransfer` and `onReceive` ensure the recipient can handle NFTs, preventing
accidental burns. Unlike fungible tokens, NFTs can’t be broken into tiny
fractions, and test-transferred in small amounts.

Stellar’s trust lines offer similar safety but apply to specific assets,
whereas safe transfer secures entire asset classes. Soroban removed trust line
requirements for contract transfers.

`safeTransferFrom` is relevant for NFT transfers to smart contracts, while
`permit` also works for EOAs, addressing the indivisibility issue. Stellar’s
built-in signatures provide `permit`-like functionality at the protocol level.
For added safety, developers can implement safe variants or leverage existing
solutions.

## Notes on `transfer()`:

- The `transfer()` function exists in ERC20 but is absent in ERC721, primarily
  for historical reasons. In both ERC20 and ERC721, `transferFrom()` can be
  used instead of `transfer()`, with the the only difference being an
  additional on-chain check. To avoid redundancy, `transfer()` was omitted from
  the ERC721 standard.
- Despite this, `transfer()` retains a key advantage over `transferFrom()`:
  when the token owner initiates the transfer, `transfer()` is more efficient
  and cost-effective, as it eliminates the need for an extra on-chain
  verification.
- While we aim for compatibility with other ecosystems, maintaining internal
  consistency within our own ecosystem takes precedence. The behavior and the
  use cases of `transfer()` remains the same for both fungible and non-fungible
  tokens, so we decided to include it for NFTs as well in this SEP.

## Notes on `name()`, `symbol()` and `token_uri()`

- Those methods are not part of ERC721, but including them in the standard,
  because exposing metadata through this API proved itself as a common practice
  for marketplaces to display NFT details. Furthermore, it’s important to be
  consistent within the Stellar ecosystem as SEP-41 also defines metadata as
  part of the core interface for fungible tokens.
- [[SEP-39](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0039.md#design-rationale)](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0039.md#design-rationale)
  suggests a dual approach for describing NFTs. The first one proposes an
  example json schema, while the other suggests leveraging the defined in SEP-1
  “Stellar.toml”. While this approach makes sense for NFTs represented by
  Classic Stellar Assets, `token_uri()` returns a URI that points to a JSON
  file that conforms to the "Non-Fungible Metadata JSON Schema".
- `token_uri()` returns a URI, not necessarily an `https://` URL. Clients
  should support `https://`, `ipfs://` and `data:` URIs; a `data:` URI carries
  the JSON inline, for a contract that generates its metadata on chain.
- For metadata that does not change, we recommend content-addressed storage
  such as [IPFS](https://ipfs.tech) or [Iroh](https://www.iroh.computer), and a
  URI that names the content (`ipfs://<cid>`) rather than a gateway URL.
- A token whose metadata changes after mint (a dynamic NFT) emits the
  `metadata` event when it does, or `batch_metadata` for a range of tokens.
- The JSON file follows the "Non-Fungible Metadata JSON Schema" below, and an
  example file comes after it.

The "Non-Fungible Metadata JSON Schema" is:

```json
{
  "title": "Non-Fungible Metadata",
  "type": "object",
  "properties": {
    "name": {
      "type": "string",
      "description": "Identifies the asset to which this NFT represents"
    },
    "description": {
      "type": "string",
      "description": "Describes the asset to which this NFT represents"
    },
    "image": {
      "type": "string",
      "description": "A URI pointing to a resource with mime type image/* representing the asset to which this NFT represents."
    },
    "external_url": {
      "type": "string",
      "description": "A URL pointing to an external resource related to the asset, for example, to visualize the NFT on the collection's own site."
    },
    "attributes": {
      "type": "array",
      "description": "Array of attributes that describe the asset",
      "items": {
        "type": "object",
        "properties": {
          "display_type": {
            "type": "string",
            "description": "The type of display for the attribute"
          },
          "trait_type": {
            "type": "string",
            "description": "The type of trait this attribute represents"
          },
          "value": {
            "description": "The value of the attribute",
            "anyOf": [
              {
                "type": "string"
              },
              {
                "type": "number"
              }
            ]
          },
          "max_value": {
            "type": "number",
            "description": "The maximum value for numeric traits"
          }
        }
      }
    }
  }
}
```

An example of a file served at `token_uri()`, whose `image` is a content
addressed URI:

```json
{
  "name": "Minimal NFT #0",
  "description": "The first token of the example.",
  "image": "ipfs://<image-cid>",
  "external_url": "https://example.com/nft/0",
  "attributes": [
    { "trait_type": "Background", "value": "Blue" },
    {
      "trait_type": "Edition",
      "display_type": "number",
      "value": 1,
      "max_value": 100
    }
  ]
}
```

A wallet typically needs only `name`, `description` and `image` to display the
token. A contract with dynamic traits can write their current value in
`attributes`, and emits `metadata` when the JSON changes. The read of the trait
stays the value to trust. A trait computed on read from another contract can be
written there as well: its value changes with that contract, without
`metadata`, and a client follows that contract for its changes, as for the read
of the trait.

## Extensions

The extensions are optional. A contract that offers one does it as written
here.

### Non-transferable (soulbound) tokens

A contract can issue tokens that cannot be transferred by their owner. It can
omit `transfer`, `transfer_from`, `approve`, `approve_for_all`, `get_approved`
and `is_approved_for_all`. It still implements `balance`, `owner_of`, `name`,
`symbol` and `token_uri`, so that wallets, marketplaces and explorers keep
reading and displaying the token.

Any change of owner, by any path (a key rotation, a recovery, a clawback by the
issuer, a migration), emits the `transfer` event with the previous and the new
owner.

For such a token the token id is the stable identity, and the address is only
its current key, which can be rotated or recovered. An integration keys its
data by `token_id`, not by address.

### Dynamic traits

A dynamic NFT carries values that change after mint, such as a rank, a level or
a score. A contract can expose them as traits, adapted from
[ERC-7496](https://eips.ethereum.org/EIPS/eip-7496). Reading a trait never
changes the state.

```rust
/// Returns the value of one trait of `token_id`. A trait defined by the
/// contract that was never set returns `0`.
///
/// # Arguments
///
/// * `e` - Access to the Soroban environment.
/// * `token_id` - Token id as a number.
/// * `trait_key` - Name of the trait.
///
/// # Notes
///
/// If the token does not exist, or the trait is unknown, this function is
/// expected to panic.
fn trait_value(e: &Env, token_id: TokenID, trait_key: String) -> i128;

/// Returns the values of several traits of `token_id`, in the order asked.
/// Same notes as `trait_value()`.
fn trait_values(
    e: &Env,
    token_id: TokenID,
    trait_keys: Vec<String>,
) -> Vec<i128>;

/// Returns the URI of the trait metadata, described below. Same kinds of URI as
/// `token_uri()`.
fn trait_metadata_uri(e: &Env) -> String;
```

Compared with ERC-7496, the key is a `String`, the value an `i128`, and the Set
Trait event carries the token id as a topic.

A contract can offer a setter, with its own rules on who is allowed to call it
(an issuer, an automated rule or the owner):

```rust
fn set_trait(e: &Env, token_id: TokenID, trait_key: String, new_value: i128);
```

Whenever a stored trait changes, by any path, the contract emits the Set Trait
event below. A change of a trait that also changes the output of `token_uri()`
(a rank that redraws the picture) comes with `metadata`.

A trait can also be computed on read from another contract, such as a score.
The token cannot emit an event when that contract changes, so a client reads
such a trait when it needs it instead of caching it from events. Whoever runs
the contract can observe the source and emit the event, which is out of the
scope of this SEP.

**Set Trait Event**

The event has topics:

- `Symbol` with value `"set_trait"`
- `TokenID`: the identifier of the token.

The event has data:

- `String`: the key of the trait.
- `i128`: the new value.

**Set Trait Metadata URI Event**

The event has topics:

- `Symbol` with value `"set_trait_metadata_uri"`

The event has data:

- `String`: the new URI.

**Trait metadata**

The document served at `trait_metadata_uri()` follows the ERC-7496 shape:

```json
{
  "traits": {
    "tier": {
      "displayName": "Tier",
      "dataType": { "type": "string" },
      "valueMappings": {
        "0": "Bronze",
        "1": "Silver",
        "2": "Gold"
      },
      "tokenOwnerCanUpdateValue": false
    }
  }
}
```

- `displayName`: the label of the trait in a UI.
- `dataType.type`: how to read the integer returned by `trait_value()`, one of
  `string` (a label found in `valueMappings`), `decimal`, `boolean` (`0` or
  `1`) or `epochSeconds`.
- `valueMappings`: the label of each integer value, for an enumeration.
- `tokenOwnerCanUpdateValue`: whether the owner of the token, as opposed to the
  issuer or the contract itself, can change the value.

`trait_metadata_uri()` returns a URI of the same kinds as `token_uri()`,
including a `data:` URI carrying the JSON inline. A contract that publishes a
new document emits `set_trait_metadata_uri`.

  - Recommend `u32` for `TokenID` and `Balance`, as the minimum for
    integrations.
  - Describe what `token_uri()` can return, with a recommendation for
