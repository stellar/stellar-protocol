## Simple Summary

Today, every piece of per-ledger randomness in Stellar derives from the last
closed ledger (LCL) hash. Because the quorum leader influences which ledger
closes and what it contains, that same leader can bias three protocol-critical
outputs that are supposed to be unpredictable: SCP nomination priority, the
Soroban PRNG seed, and the order in which transactions apply.

This CAP replaces that leader-influencable randomness with a **multi-validator,
aggregated, delayed-reveal randomness beacon** built from a **Verifiable Random
Function (VRF)** — `ECVRF-EDWARDS25519-SHA512-TAI` (RFC 9381), whose building
block is currently proposed in
[#5409](https://github.com/stellar/stellar-core/pull/5409) and is not yet
merged. Rather than let a single self-selected validator pick the entropy
(which reintroduces a leader bias at a higher layer), every validator
contributes one private-key-bound pseudorandom value, the values are committed
two ledgers ahead, revealed and verified one ledger ahead, and the aggregate is
committed in a finalized `StellarValue` **before** the ledger it randomizes
begins. The result is a single shared, unpredictable, verifiable beacon per
ledger that removes the prior-ledger "grinding" surface of the current design,
prevents any single key holder from re-rolling or predicting the outcome, and
removes the arbitrary leader selection of the entropy source.

## Motivation

### The problem: leader-influencable randomness

The Stellar protocol currently derives all per-ledger randomness from the hash
of the last closed ledger (the LCL). Concretely:

| Consumer | Call site | Today |
|---|---|---|
| Nomination priority | `SCPDriver::computeHashNode` | `hashHelper(slot, prev, round, nodeID)` — the LCL hash leaks into priority |
| Soroban PRNG | `LedgerManagerImpl` (`sorobanBasePrngSeed`) | derived from `txSet.getContentsHash()` |
| Transaction apply order | `TxSetFrame` (`ApplyTxSorter`) | deterministic shuffle keyed off `getContentsHash()` |

Because the LCL hash is determined *before* the next nomination round begins,
and because the quorum leader influences *which* ledger closes, a leader can
search for a favorable LCL hash before committing — a classical **grinding
attack**. The consequence is that a single actor gets measurable control over
values the protocol presents as unpredictable.

### Why a VRF, and why a naive single-leader VRF is not enough

A VRF evaluation `beta = VRF_prove(sk, alpha)` satisfies:

- **Pseudorandomness** — for anyone without `sk`, `beta` is indistinguishable
  from random until it is revealed.
- **Uniqueness** — for a fixed `(sk, alpha)` there is at most one valid `beta`;
  the producer cannot produce two.
- **Verifiability** — with `pk`, `alpha`, `beta`, and the proof `pi`, anyone
  can check `beta` was honestly derived (RFC 9381, §3).

These properties fix the input-selection failure at the *transaction-set* layer.
But a design in which a **single** validator self-selects as leader by
evaluating its own VRF over a transcript leaves four weaknesses that were called
out during review and that this CAP is written to close:

1. **Prior-ledger grinding.** Binding the VRF input to the already-finalized
   ledger `N` is not enough: the proposer closing `N` controls `N`'s
   transaction set and header, can evaluate its own VRF over every candidate
   `T(N)`, and externalize the version yielding a favorable outcome for `N+1`.
   The transcript is fixed only *after* that choice has already been exercised.
2. **Reveal / no-reveal choice.** A key holder can compute `beta` immediately,
   inspect the resulting priority and sub-seeds, and then decide whether to
   reveal it — a "selective-abort" bias even when it cannot re-roll.
3. **Information cycle.** A peer's `beta` only arrives inside its nomination,
   so a remote node cannot observe the priority input before deciding how to
   vote for it.
4. **Composite-candidate ambiguity.** SCP combines accepted nominations into a
   composite value; "the winning candidate's beta" is not well defined when
   multiple values advance.

The central design statement of this CAP is therefore: **the VRF proves a value
is pseudorandom and key-bound, but the *protocol* must guarantee there is no
meaningful choice among randomness outcomes** — not by one producer, and not by
whoever closes the ledger being referenced. We do that with an **aggregate of
many independent contributions, committed and revealed on a strict, fixed
latency**, so no single actor controls enough of the inputs to steer the
outcome. This is the primary acceptance criterion for the migration.

### Goals Alignment

This CAP is aligned with the following Stellar Network Goals:

* The Stellar Network should run at scale and at low cost to all participants
  of the network — this hardening incurs sub-millisecond cost for nominating
  nodes and no new key infrastructure.
* The Stellar Network should be a highly secure and reliable public network —
  removing a known leader-influence vector strengthens fairness and
  cryptographic hygiene for a consensus-critical system.

## Abstract

This CAP introduces protocol-level, VRF-derived, **aggregated** randomness.
Each validator contributes one domain-separated VRF output per target ledger.
A commit is published two ledgers ahead; the reveal is verified against the
committed hash and the validator's public key one ledger ahead; and the
**aggregate beacon** for the target ledger is `SHA-256` over the verified
reveals, written into the *already-finalized previous* `StellarValue`. Because
the beacon is finalized and public before the ledger it randomizes begins, and
because it is a hash over many independent contributions, no single proposer or
key holder obtains meaningful choice among randomness outcomes. Independent,
labeled **sub-seeds** are derived from the shared beacon for nomination
priority, the Soroban PRNG, and transaction apply order.

The cryptographic building block (`ECVRF-EDWARDS25519-SHA512-TAI`, RFC 9381)
ships upstream in stellar-core PR #5409 (currently under review, not merged),
complete with RFC 9381 test vectors, secret zeroization, canonical-point and
full-decode enforcement, and a fallible encode-to-curve path. This CAP depends
on that primitive and specifies its *protocol-level use*: the transcript
format, the commit/reveal timeline, the aggregation and fallback rule, the
sub-seed derivation, and the adversarial conformance vectors.

## Specification

### Design overview

The core moves: (a) the entropy source **before** the object being randomized,
(b) leadership/priority fairness away from any single self-selected value, and
(c) the entropy into a **shared beacon** that is immutable before the slot
begins. The randomizing unit is a **slot** `s` (a ledger being generated); its
entropy `B(s)` is finalized at the close of ledger `s-1`.

For each slot `s`:

1. **Transcript.** Each validator builds a canonical per-slot transcript
   `T(s)` (Section "Canonical transcript"), anchored to the **already-finalized
   header of ledger `s-3`** so the value is fixed before the commit phase
   begins and cannot be re-rolled by whoever closes `s-2` or `s-1`.
2. **Commit phase (ledger `s-2`).** Each validator `v`
   evaluates `beta_v = VRF_prove(sk_v, T(s))`, computes the hiding commit
   `C_v = SHA-256(beta_v)`, and publishes `C_v` while `s-2` is being decided.
   The commit hides `beta_v` from every other node.
3. **Reveal phase (ledger `s-1`).** Each validator that committed reveals
   `(beta_v, proof_v)`. Nodes reject any reveal whose `SHA-256(beta_v)` does not
   match the earlier `C_v`, or whose VRF proof does not verify against `pk_v`
   and `T(s)`. Verified reveals are accumulated.
4. **Finalization (close of `s-1`).** `B(s) = SHA-256( || of verified beta_v
   sorted by nodeID )` is committed into `StellarValue(s-1).vrfBeaconNext`
   (Section "XDR changes"). It is now public and immutable.
5. **Use (slot `s`).** Every node derives the labeled sub-seeds (Section
   "Sub-seed derivation") from `B(s)` and uses them for nomination priority,
   the Soroban PRNG, and transaction apply order.

Because step 4 happens at the close of `s-1` — before nomination for `s`
begins — there is no information cycle, no per-candidate "winning beacon"
ambiguity, and every node computes the identical priority basis from the same
public beacon. Because `B(s)` is a hash over many independent, hidden-then-
verified contributions, no single proposer or key holder can steer it.

### Canonical transcript

The per-slot transcript is the concatenation of fixed, canonicalized fields:

```
T_b(s) = "stellar-vrf" | 0x01 | network_id | slot | purpose(=0x01) | prior_context(s)
```

Where:

| Component | Meaning | Length / type |
|---|---|---|
| `"stellar-vrf"` | ASCII static label | 11 bytes |
| `0x01` | transcript version byte (bump on any breaking change) | 1 byte |
| `network_id` | `Application::getNetworkID()` = `SHA-256(network passphrase)` | 32 bytes |
| `slot` | `ledgerSeq` of the ledger being generated (`s`), big-endian | 4 bytes |
| `purpose` | single-purpose label (see below) | 1 byte |
| `prior_context(s)` | canonical hash of the anchor ledger `s-3` (below) | 32 bytes |

Crucially, `network_id` here is the **existing** 32-byte Stellar network id
exactly as produced by `Application::getNetworkID()` — `SHA-256` of the network
passphrase, with no prefix — so transcripts built by any implementation match
the values derived from the standard API. It is **not** `0x00`-prefixed or
otherwise re-encoded.

Only **one** transcript is ever *proved* and committed per slot: the beacon
transcript `T_b(s)`, whose `purpose` byte is the dedicated **beacon purpose**
`0x01`. The consumers never prove a separate transcript — they each derive a
local, domain-separated **sub-seed** from the single beacon `B(s)` through
sub-seed purpose labels (below). This resolves any "unlabeled contribution"
ambiguity: there is exactly one commit/reveal/beacon per validator per slot, and
it proves `T_b(s)` (purpose `0x01`); the three consumers carry no extra
contribution and no extra proof.

The `purpose` byte of `T_b(s)` is:

| Value | Purpose |
|---|---|
| `0x01` | beacon proof (the single proved contribution per slot) |

And the **sub-seed** purpose labels used to derive the three consumer values are:

| Label | Consumer |
|---|---|
| `0x02` | leader / nomination-priority fairness |
| `0x03` | Soroban PRNG seed |
| `0x04` | transaction apply order |

`prior_context(s)` is exactly the existing canonical **`LedgerHeader` hash** of
ledger `s-3`:

```
prior_context(s) = LedgerHeaderHash(s-3)
```

where `LedgerHeaderHash(s-3)` is the canonical 32-byte `LedgerHeader` hash that
is already computed, stored, and cross-referenced throughout Stellar's ledger
history for ledger `s-3` (the `prevHash` chaining the following ledger). It is
used **directly** and is **not** hashed a second time — this avoids any ambiguity
between hashing a serialized header once versus hashing an already-computed
header hash. `s-3` is finalized before the commit phase for slot `s` begins.
Anchoring two ledgers further back than the commit phase guarantees the
transcript is frozen before any proposer could re-roll it while choosing what
to commit or reveal.

### Commit and reveal

Commits and reveals must be **consensus-bound and replayable** so that every
node (including one doing history/catchup replay) derives the identical beacon
for slot `s` and accepts or rejects the same `StellarValue`. The commit set is
therefore part of the consensus-visible value, not ephemeral SCP gossip:

* **Contributor set (deterministic, from consensus data).** The eligible
  contributors for slot `s` are exactly the validators whose authenticated
  commitments appear in `StellarValue(s-2).vrfCommits` — i.e. `Q` is read
  **from the consensus-visible value itself**, not derived from observed SCP
  envelopes (which can differ across nodes and omit non-signing histories).
  Each `VRFCommit` authenticates its `nodeID` with an Ed25519 signature over
  `"stellar-vrf/commit" | 0x01 | network_id | slot | commitHash` using that
  validator's existing NodeID key, so an entry attributed to an arbitrary node
  cannot inflate `Q` without that node's key. `Q` is therefore the same,
  authenticated, consensus-final set on every node; there is no per-node
  "configured threshold" and no ambiguity about who contributes.
* **Commit (ledger `s-2`).** Each contributor `v` computes
  `C_v = SHA-256(beta_v)` and the commit set
  `commit_set(s) = { (NodeID_v, C_v, sig_v) }` is recorded **in the externalized
  `StellarValue(s-2)`** (Section "XDR changes", `vrfCommits`). Because it is
  part of the consensus value, catchup nodes replay the exact same commit set.
  The `C_v` are hiding, so `beta_v` stays private until reveal. Commits are
  canonicalized with the contributor set **strictly ascending** by `NodeID`,
  with exactly one entry per contributor.
* **Reveal (ledger `s-1`).** Each contributor reveals `(beta_v, proof_v,
  transcriptHash_v)`. A node MUST accept a reveal iff:
  1. `nodeID_v` is in `commit_set(s)` (a contributor, not an interloper),
  2. it is the only reveal for `nodeID_v` (duplicates MUST be rejected), and
     entries are `NodeID`-strictly-ascending,
  3. `SHA-256(beta_v) == C_v` from the committed set (binding to the value that
     was already consensus-final at `s-2`),
  4. `transcriptHash_v == SHA-256(T_b(s))` (exact equality is a **mandatory**
     validity rule, so a proposer cannot vary this field to grind the header),
  5. `VRF_verify(pk_v, T_b(s), beta_v, proof_v)` succeeds.
  Every node derives the same accept/reject outcome from the committed set and
  the reveals. Accepted reveals are recorded in `StellarValue(s-1).vrfReveals`,
  with the *full* consensus-visible reveal set carried so replays recompute the
  identical beacon.
* **Reveal-set inclusion (deterministic).** Because a value author could
  otherwise select an arbitrary threshold-satisfying subset, the reveal set MUST
  contain **every** `commit_set(s)` member whose verifiable reveal was observed
  during `s-1`; a reveal that verifies under the three rules above cannot be
  omitted by the value author. (The residual that a *majority-colluding* set can
  withhold its own reveals — or that no-other-verified-reveal can be proven
  absent from history — is the threshold-reconstruction case, stated in
  Non-goals and future work, not solved here.)
* **Aggregation (close of `s-1`).** `B(s)` is derived from the accepted
  reveals (below) and written into `StellarValue(s-1).vrfBeaconNext`.

Only reveals from the committed contributor set that pass all five checks are
aggregated. Everything needed to reconstruct `B(s)` deterministically — the
commit set (`s-2`), the reveals (`s-1`), and the canonical aggregation rule —
is consensus-bound, so a stale or adversarial node cannot observe a different
set and disagree about whether a `StellarValue` is valid.

### Beacon aggregation and fallback

```
B(s) = SHA-256( alpha_1 || alpha_2 || ... || alpha_k )
```

where `alpha_i` are the *verified* `beta_v` from the accepted reveal set,
ordered lexicographically by `NodeID` ascending, and `k` is the number of
accepted reveals. The ordering (and therefore `B(s)`) is deterministic and
identical on every node; it does not depend on the order in which reveals
arrived.

**Threshold rule (deterministic).** Let `Q` be the size of the committed
contributor set for slot `s` (consensus-final at `s-2`). Define the required
threshold as:

```
t = floor(2*Q/3) + 1
```

i.e. **strictly more than two thirds** of the committed contributor set
(`floor(2Q/3)+1 > 2Q/3`). Every node derives the same `t` from the same `Q`.
This is a *majority-of-committed-contributors* acceptance rule chosen to keep
the beacon live under honest-majority partial reveals; it is **not** the FBA
externalization threshold (which is determined by quorum-set topology, not by a
global count), and the CAP does not claim otherwise.

* **Sufficient reveals:** if `k >= t`, `B(s)` is the aggregate above.
* **Insufficient reveals (graceful liveness degradation):** if `k < t` by the
  close of `s-1`, the beacon degrades to status-quo LCL entropy:

  ```
  B(s) = SHA-256( LedgerHeaderHash(s-2) )
  ```

**Fallback threat model (honest).** To force the fallback (`k < t`) an
adversary must prevent contributors from *revealing*, i.e. keep the accepted
reveal count below `t`. That means suppressing `Q - t + 1` reveals. With
`t = floor(2Q/3)+1`, that is roughly `ceil(Q/3)` reveals —**about a one-third
coalition can force the fallback**, which it does by withholding its own
reveals. The CAP does **not** claim this requires quorum control. The honest
property is narrower and precise:

* While `k >= t` holds with an honest-majority contributor set, no single key
  holder and no minority can predict, re-roll, or steer `B(s)`.
* If a (roughly) one-third coalition withholds, the protocol remains live but
  falls back to the LCL-derived value — i.e. entropy degrades to today's
  already-documented adversary-influenced level. The fallback is a **liveness**
  guarantee, not a security guarantee.
* Eliminating the residual that a colluding majority can steer by withholding
  (threshold reconstruction, where any subset recreates a withheld reveal) is
  explicitly out of scope and flagged for follow-up in Non-goals.

### Sub-seed derivation

`B(s)` is a single 32-byte beacon. We never consume it directly; each consumer
derives an independent 32-byte sub-seed through a domain-separated keyed
derivation, preventing cross-purpose reuse:

```
subseed(p) = SHA-512( "stellar-vrf/sub" | 0x01 | network_id | slot | p | B(s) )[0:32]
```

Using independent labels means a favorable outcome for one purpose cannot steer
another. Each consumer then substitutes its sub-seed exactly where today's
LCL-derived value is used:

| Consumer | Uses |
|---|---|
| Nomination priority | `hashHelper(..., subseed(0x02))` replaces the LCL-hash-derived priority entropy |
| Soroban PRNG | `sorobanBasePrngSeed = subseed(0x03)` |
| Apply order | shuffle key = `SHA-256(subseed(0x04) ‖ txHash)` |

Because `B(s)` is shared and public before slot `s` begins, every candidate's
priority is computed from the same unpredictable entropy, so no single nominee
gains a priority advantage from its own VRF, and no ambiguity arises when SCP
combines nominations into a composite value.

### XDR changes

This patch of XDR changes is based on the XDR files in commit
`03cbf40cec4d89f82171bf895ef7598458d83e1b` of `stellar-xdr`, following the
`#ifdef`-gating precedent of CAP-0088. It is additive and versioned.

The randomness machinery is carried as **new orthogonal top-level fields and
types** of/alongside `struct StellarValue`, not as new arms of the `ext` union.
This is deliberate: `StellarValue.ext` is a single discriminated union whose
arms enumerate value-shape variants (including CAP-0088's `MS_CLOSE_TIME` arms).
Adding randomness as another union arm would make it mutually exclusive with
those already-active arms — a VRF-driven value could not also carry millisecond
close time or the empty-tx-set metadata. Orthogonal fields coexist with any
`ext` arm while keeping commit/reveal records consensus-visible and replayable:

`vrfCommits` carries the hiding commit set for slot `L+2` (published during
ledger `L`); `vrfReveals` carries the verified reveals for slot `L+1`; and
`vrfBeaconNext` is the resulting 32-byte aggregate `B(L+1)`. All three are
`Hash`/`opaque[64]`/`opaque[80]` of **exact** width — no variable-length
`opaque<...>` — so a malformed or truncated value cannot be encoded, and the
`Hash` type (`opaque Hash[32]` in `Stellar-types.x`) matches the `SHA-256`
width used throughout this CAP.

`VRFCommit.sig` is an Ed25519 signature by `nodeID`'s existing NodeID key over
`"stellar-vrf/commit" | 0x01 | network_id | slot | commitHash`, so a value
author cannot inject a commit attributed to a node that never committed (which
would inflate `Q` and force fallback); the signature is verified before the
entry can contribute to `Q`. Both vectors are **bounded** by the named protocol
cap `MAX_VRF_CONTRIBUTORS = 100`, and a value whose vector exceeds the cap, that
is not strictly `NodeID`-ascending, or that contains a duplicate `NodeID` is
rejected **before** any per-reveal cryptographic verification — so an oversized
or malformed candidate cannot force unbounded bandwidth, allocation, or
verification work.

Because the commit set and reveals are consensus-visible and replayable, a node
doing history/catchup replay reconstructs the exact same commit set, reveals,
and aggregate `B(L+1)` that the original close derived — there is no hidden
per-node local state that could make two nodes disagree on whether a
`StellarValue` is valid.

The `GeneralizedTransactionSet` itself is **unchanged**. The `ext` union is
**unchanged** (no new arms; the CAP-0088 arms are untouched and remain
selectable). Verification is localized: every node recomputes `B(s)` from the
committed set and accepted reveals (all consensus-visible) and checks it equals
`StellarValue(s-1).vrfBeaconNext` before using it, and non-matching values are
rejected.

**On `#ifdef` vs. a wire discriminant.** The `#ifdef VRF_RANDOMNESS` in this
diff is the *source-tree* gating used by every CAP (including CAP-0088) to keep
the new types and members conditional until the protocol version that emits
them is enabled; it is **not** a run-time wire discriminant. At the wire level,
the presence of these members is a function of the **frozen protocol version**
(split by `LedgerUpgradeType::LEDGER_UPGRADE_VERSION`), exactly as CAP-0088's
members are. The reason they are trailing top-level fields rather than `ext`
arms is deliberately *not* a way to smuggle history: `ext` is a single
discriminated union and each arm is mutually exclusive, so adding a VRF arm
would prevent a VRF-carrying value from also carrying `MS_CLOSE_TIME` — the
orthogonal fields exist precisely so a value can carry both, while old XDR
cannot decode the new protocol-version framing at all (the same strict boundary
CAP-0088 enforces for its new arms). Historical/pre-upgrade values never
serialize the VRF members because they are produced under a protocol version in
which the members are not yet emitted; the version gate, not the preprocessor,
defines what is on the wire.

### Semantics

**Nomination.** A node nominating for slot `s` uses `B(s)` — already finalized
in `StellarValue(s-1)` — to compute `subseed(0x02)` and thereby the priority
basis of each candidate. All nodes share `B(s)`, so priorities are
deterministic, unpredictable in advance, and identical across the network for a
given `(slot, prev, round, nodeID)`.

**Verification.** Before a node uses `vrfBeaconNext` of ledger `L`:

1. Reconstruct `T_b(s)` for `s = L+1` from `network_id`, `slot`, and the
   finalized `LedgerHeader(s-3)`.
2. Reject `vrfCommits`/`vrfReveals` that exceed `MAX_VRF_CONTRIBUTORS`, are not
   strictly `NodeID`-ascending, or contain a duplicate `NodeID`.
3. Re-verify each aggregated reveal: `SHA-256(beta_v) == C_v`,
   `transcriptHash_v == SHA-256(T_b(s))` (exact equality, mandatory), and
   `VRF_verify(pk_v, T_b(s), beta_v, proof_v)` valid.
4. Recompute `B(s)` and require it equals `StellarValue(L).vrfBeaconNext`.

The stored beacon and the locally recomputed aggregate MUST agree; otherwise the
value is treated as invalid and not externalized.

**Soroban PRNG and apply order.** Once `B(s)` is accepted, every node derives
`subseed(0x03)` and `subseed(0x04)` and uses them exactly where it uses the
LCL-derived values today. The change is localized to the three consumers; the
surrounding consensus, fee, and execution machinery is untouched in this CAP.

### Non-goals

This CAP does **not** change transaction inclusion or censorship properties:
leaders still choose which transactions are included (a deliberate, documented
case in issue #4388). It does not introduce a new key type — the existing
Ed25519 node key is reused as the VRF key, keeping StrKey formats and tooling
unchanged. It does not attempt a fully non-grindable RANDAO-style beacon under
a byzantine-majority adversary: forcing the fallback requires preventing a
supermajority of the deterministic contributor set from revealing, which is
equivalent to controlling consensus and is explicitly out of scope. It does not
attempt **threshold reconstruction** — eliminating the bounded last-revealer
in/out choice by letting any subset reconstruct a withheld contribution —
which is explicitly scoped out and flagged for follow-up. Cross-validator key
rotation and slashing are out of scope and flagged for follow-up.

## Design Rationale

### Why the aggregate beacon, not a single self-selected leader

The simplest VRF design — each validator self-selects as leader by evaluating
its own VRF and presenting `beta` inside its nomination — fails the review
criteria on four counts (prior-ledger grinding, reveal/no-reveal bias,
information cycle, and composite-candidate ambiguity). An aggregate beacon
dissolves all four at once:

* **Shared input.** `B(s)` is a single public value consumed by all nodes, so
  there is no per-candidate "winning beacon" and no composite ambiguity.
* **Many contributors.** No single key holder controls `B(s)`; its own reveal
  is one term mixed into `SHA-256` over many. This removes *re-rolling* (a
  committed value cannot be changed) and *prediction* (the aggregate is
  pseudorandom until the reveal set is frozen), and removes the prior-ledger
  grinding surface of a single self-selected leader.
* **Fixed latency.** Commits are frozen at `s-2`, reveals are verified and
  aggregated at `s-1`, and the aggregate is committed at the close of `s-1` —
  before `s` begins, so no information cycle and no feedback into the randomized
  object.

### Boundaries of the reveal/withholding model (honest statement)

The commit/reveal construction removes re-rolling, prediction, and prior-ledger
grinding, and it removes a *withholding* lever in the sense that a contributor
cannot steer the final aggregate toward a favorable value it has already
computed (its own term is one unpredictable input among many). It does **not**,
by itself, eliminate the **last-revealer in/out choice**: a contributor that
reveals last can observe the other published reveals, compute the aggregate
with and without its own `beta_v`, and choose which of the two to leave in the
record, so long as the remaining accepted set still meets the threshold `t`.
Because both candidate outcomes are pseudorandom and unsteerable by that
contributor (it cannot make "beta_v in" favorable to itself — it only decides
whether its own term is present), this is a *bounded* two-outcome choice rather
than a re-roll or a grinding surface; but it is a real residual choice that this
CAP does not claim to remove.

Eliminating it entirely requires a Threshold Randomness construction in which
any subset of contributors can *reconstruct* a withheld contribution — e.g.
Shamir/two-round reconstruction where the beacon is a function of all committed
values even if some reveals are withheld. That construction is explicitly
out of scope for this CAP and flagged for follow-up (Section "Non-goals"). The
conformance vectors pin exactly the properties this CAP does guarantee (no
prior-ledger grinding, no re-roll, no cross-network/slot reuse, purpose
separation) and do not overstate the withholding guarantee.

### Why the transcript anchors to `s-3`, and how grinding is bounded

Binding to "the prior ledger" is insufficient, because whoever closes that
ledger controls its contents. This CAP anchors the transcript to ledger `s-3`,
which is finalized **before** the commit phase at `s-2` — so the anchor itself
cannot be re-rolled while commits are being made, and the `s-2`/`s-1` proposers
cannot select among alternative `T(s)` values. The residual theoretical surface
— an adversary that controls the closure of `s-3` and thus the single anchor —
is bounded by two independent facts: the adversary would have to choose a
favorable anchor *blind*, before the honest contributions are committed or
revealed, and the aggregate over honest contributions is pseudorandom and
unpredictable to it. As long as the honest-majority committed contributor set
keeps revealing (`k >= t`), the beacon the adversary cannot steer. Forcing the
fallback instead means suppressing `Q - t + 1` reveals — with
`t = floor(2Q/3)+1`, roughly a one-third coalition withholding its own reveals
— at which point the protocol stays live on the LCL-derived fallback (see
"Beacon aggregation and fallback"); that is a liveness degradation, not a
grinding surface, and the residual colluding-majority steer is stated in
Non-goals.

### Why the strict commit/reveal latency

The strict two-ahead / one-ahead latency is what makes the hidden-then-verified
flow sound: a reveal must match a commit made before the revealer could know
which reveal would be favorable to itself. This prevents both re-rolling (the
commit binds the value) and post-compute substitution.

### Why an orthogonal top-level field in `StellarValue`

`StellarValue.ext` is a single discriminated union; adding VRF as another arm
would make it mutually exclusive with the CAP-0088 `MS_CLOSE_TIME` arms.
Orthogonal gated fields coexist with every existing `ext` arm, keep the commit
set and reveals consensus-visible and replayable, and use only `Hash`/fixed
`opaque[n]` types matching the `SHA-256` width used throughout this CAP. This
directly addresses the "preserve all already-active semantics" requirement
raised in review.

### Why labeled sub-seeds from one beacon

Reusing one value directly across nomination, the PRNG, and apply order would
let a favorable PRNG outcome double as a favorable order outcome. Deriving
independent, labeled sub-seeds bounds each purpose to its own 32 bytes of
entropy. This is the same domain-separation discipline recommended in review and
used by the RFC's own ciphersuite labels, and it makes the "purpose separation"
conformance vector trivially checkable.

### Related work

Aggregated VRF/delayed-reveal randomness is well established — RANDAO and
drand use commit-reveal aggregation, Algorand and Ouroboros use VRF sortition,
and RFC 9381's ciphersuite labels use domain separation. This CAP is deliberately
conservative: it reuses existing Ed25519 keys, keeps the three consumers
localized, adds a compact, replayable commit/reveal/beacon record to the
consensus value, and lands the crypto as a separately-reviewed primitive first
(PR #5409), so the protocol change is small and auditable.

## Protocol Upgrade Transition

This is a protocol upgrade and ships behind a new protocol version in
`LedgerUpgradeType::LEDGER_UPGRADE_VERSION`. Under the legacy protocol version,
the three VRF fields (`vrfCommits`, `vrfReveals`, `vrfBeaconNext`) are absent
(`#ifdef VRF_RANDOMNESS`) and the LCL-derived randomness is unchanged.

The VRF fields are new serialized trailing members of `StellarValue`. Old XDR
schemas cannot decode unknown trailing members and old protocol code does not
derive sub-seeds from a beacon, so — exactly as CAP-0088 requires for its new
arms — the upgrade boundary is strict: **a node MUST upgrade both its XDR schema
and its validator/apply logic to the protocol version that emits these fields
before the first VRF beacon is produced.** Per the existing protocol-version
gate, the network flips to the new version only when a quorum of validators is
upgraded; nodes that have not upgraded cannot externalize a value carrying the
VRF fields and will buffer until their version matches, the same synchronization
model as CAP-0088 (see `core/cap-0088.md`). No "old node derives the same value
from the new format" claim is made, because old nodes cannot interpret the new
format at all; correctness is guaranteed by the version gate.

The hard prerequisites before this protocol version ships are the XDR frozen
with this CAP (`VRFCommit`/`VRFReveal` and the three `StellarValue` fields) and
the commit/reveal/aggregation timeline, both pinned here.

**Warm-up transition.** The two-ahead/one-ahead pipeline cannot start at the
strict boundary: the first VRF-enabled slot `s0` needs commits carried in
`StellarValue(s0-2)` and reveals in `StellarValue(s0-1)`, but those legacy ledgers
(before the version flip) do not serialize the VRF fields. The transition
therefore warms up in three phases, consuming the legacy LCL-derived entropy
for the affected consumers in each phase:

1. **Phase A (version flip, commits only).** The network begins emitting
   `vrfCommits` for future slots, but `vrfReveals` and `vrfBeaconNext` are not
   yet required. All randomness consumers continue to use today's LCL-derived
   values. Bounded duplicates/ordering rules apply from the first carried
   vector.
2. **Phase B (reveals).** The network begins carrying verified `vrfReveals`
   for the slots that had commits in Phase A, producing a beacon — but that
   beacon is **not yet consumed** for nomination/PRNG/apply-order; consumers
   still use the LCL-derived source. This lets an implementation validate the
   aggregation pipeline end-to-end without depending on it for liveness or
   fairness.
3. **Phase C (consumption).** Once the pipeline has produced a full
   commit→reveal→beacon cycle for consecutive slots, the three consumers flip
   to `subseed(0x02/0x03/0x04)` of the shared beacon. From this point the rule
   in "Beacon aggregation and fallback" applies (fallback to
   `SHA-256(LedgerHeaderHash(s-2))` keeps the network live if reveals are
   withheld).

Phase C is reached only when the network has externallyed, on the new protocol
version, a run of ledgers that each carry a committed set for `L+2`, reveals
for `L+1`, and the frozen beacon — i.e. the prerequisite "both prior stages
exist" is satisfied from consensus-visible state, never from per-node memory.
Until Phase C, the legacy source of entropy is explicitly in force, so the
warm-up introduces no window in which randomness is missing.

## Backwards Incompatibilities

This CAP changes consensus-visible data (a new optional `StellarValue` member)
and the source of per-ledger randomness, and is gated behind a new protocol
version:

* The new member is gated by `#ifdef VRF_RANDOMNESS`; by construction it
  serializes only on the new protocol version.
* The behavior of the three randomness consumers changes only on the new
  protocol version.
* No change to balances, operations, or existing account semantics.
* The `ext` union (including the CAP-0088 `MS_CLOSE_TIME` arms) is untouched and
  remains fully selectable on the new version.

The consequence of a mis-verified beacon (or a node on the new version running
with stale reveal state) is that it fails to externalize the invalid value —
the same failure mode as an invalid signature today. Verification is
deterministic and self-consistent, so all honest nodes on the new version agree.

### Resource Utilization

* **Compute:** one VRF evaluation per validator per target slot (commit phase)
  and two scalar multiplications for verification per reveal (all nodes),
  amortized across the two-ledger window; sub-seed derivation is a single
  `SHA-512` per consumer per slot. Total additional work is sub-millisecond and
  negligible versus SCP round time.
* **Memory/bandwidth (XDR, per contributor, before vector framing):**
  `NodeID` is 36 bytes (4-byte `PublicKey` union discriminant + 32-byte key).
  A `VRFCommit` is therefore **~132 bytes** (NodeID 36 + `commitHash` 32 +
  `sig` 64), a `VRFReveal` is **~212 bytes** (NodeID 36 + `vrfBeta` 64 +
  `vrfProof` 80 + `transcriptHash` 32), and the aggregate beacon is a fixed
  **32 bytes**. Both vectors are bounded by `MAX_VRF_CONTRIBUTORS = 100`, so
  the worst-case consensus footprint is about
  `(132 + 212) · 100 + 32 ≈ 34.4 KiB` per `StellarValue` — carried per ledger,
  not per transaction. The `GeneralizedTransactionSet` is unchanged.
* **Disk/database:** the consensus-visible commit/reveal/beacon records per
  ledger in `StellarValue` (needed for deterministic replay), plus the bounded
  in-memory reveal bookkeeping during the two-ledger window.

## Security Concerns

The security argument rests on three properties, each tied to a conformance
vector in the Test Cases section:

1. **No meaningful input selection (grinding is bounded).** The transcript is
   anchored to ledger `s-3`, finalized before the commit phase; the beacon is an
   aggregate over many committed-then-revealed contributions. A proposer cannot
   select among randomness outcomes by choosing `s-3`'s contents (frozen before
   commits), `s-2`'s contents (commits are hidden), or `s-1`'s contents (reveals
   are already committed). *Covered by the prior-ledger grinding vector.*
2. **No re-roll; bounded withdrawal.** A key holder cannot re-roll (the commit
   binds its value) and cannot predict or steer the aggregate with its own single
   contribution. Withholding removes only its own term; forcing the fallback
   requires preventing a supermajority of the deterministic contributor set from
   revealing, which is equivalent to controlling consensus and out of scope. As
   stated in the Design Rationale, a *last* revealer retains a bounded in/out
   two-outcome choice; eliminating it (threshold reconstruction) is out of scope
   and flagged for follow-up. *Covered by the single-contribution-withholding
   vector.*
3. **Independence of purposes (domain separation).** Each consumer derives from
   a labeled sub-seed, so outcomes across purposes are independent. *Covered by
   the purpose-separation vector.*

Security does not depend on keeping any value private after the reveal window
(the beacon is public); it depends on **unique, committed inputs** (one legal
reveal per output, bound by the previously committed hash), **unpredictability
of the aggregate until it is frozen**, and the **deterministic contributor set
and threshold rule**. All three are enforced by the primitive (RFC 9381
uniqueness), by the commit/reveal binding, and by this CAP's consensus-visible,
replayable commit/reveal/aggregation pipeline.

A validator's long-term signing key is used as its VRF key, so the key is
exposed to the same threat model as today's Ed25519 signing key. The building
block hardens this with constant-time operations and full secret zeroization
(PR #5409), and no new key-rotation obligation is introduced. Post-quantum
hardening and cross-validator key rotation are explicitly out of scope here.

## Test Cases

The following **adversarial conformance vectors** are required for any
implementation of this CAP. They prove Stellar's *use* of the VRF and the
aggregation/delaying rules, complementing the RFC 9381 vectors that prove the
primitive. Each is a deterministic, executable acceptance test with a fixed
transcript, fixed public contributions, and a fixed expected outcome.

| # | Vector | Purpose | Expected |
|---|---|---|---|
| V1 | prior-ledger grinding | A proposer varies candidate versions of the *anchor* and of the *commit/ reveal ledgers* (`s-3`, `s-2`, `s-1`) and observes the beacon. | The aggregate is invariant once the commit set is frozen: varying the unfinalized `s-1` candidate, or reordering reveals, does not change `B(s)`; the anchor `s-3` is chosen blind, before any honest commit exists. |
| V2 | single-contribution withholding | A validator withholds its reveal for `s`. | `B(s)` is recomputed over the remaining verified reveals, NodeID-ordered; the withheld value is excluded. With `Q` contributors and threshold `t = floor(2Q/3)+1`, withholding a single reveal cannot force the fallback or steer the aggregate toward a favorable value; the fallback (`k < t`) is re-entered only when `Q - t + 1` (roughly a one-third) coalition withholds, which is the liveness boundary, not a grinding surface (see "Beacon aggregation and fallback"). The vector asserts both the single-withhold outcome and the `k >= t` branch admission. |
| V3 | commit/reveal binding | A reveal whose `SHA-256(beta)` does not match the committed `C_v`, or whose proof does not verify, is submitted. | Verification MUST reject the reveal; it MUST NOT enter the aggregate. |
| V4 | cross-network replay | A beacon committed on testnet is replayed onto mainnet. | Verification MUST fail because `network_id` differs, so `T(s)` (hence every contributor's `beta_v` and the aggregate beacon) differs. *The fixture pins network-scoped betas so the two networks' beacons provably differ.* |
| V5 | cross-slot replay | A beacon for slot `s` is replayed against slot `s+1`. | Verification MUST fail because `slot` differs (transcript mismatch) and the finalization ledger differs. |
| V6 | purpose separation | The same `B(s)` is consumed by two purposes. | `subseed(0x02)`, `subseed(0x03)`, and `subseed(0x04)` MUST be pairwise distinct, so a favorable outcome for one consumer cannot be reused for another. |
| V7 | malformed contribution / wrong key | A contribution whose beta does not bind to its committed `C_v`, that carries the wrong `transcriptHash`, or that is attributed to the wrong NodeID is submitted. | The protocol verifier (the same acceptance path used before aggregation) MUST reject it: a beta that does not bind to the committed hash, a `transcriptHash != SHA-256(T_b(s))`, or a serialized entry attributed to a NodeID that did not commit to that `C_v` cannot enter the aggregate. *(RFC 9381 proof and wrong-public-key rejection is exercised by the PR #5409 harness; the protocol layer here pins ordering, binding, `transcriptHash`, and NodeID-attribution rejection.)* |
| V8 | transcript / beacon mutation | Any byte of `B(s)` or of `T(s)` is altered after finalization. | The recomputed aggregate no longer matches the committed `vrfBeaconNext`; verification MUST reject. |

V1, V2, and V8 are the most critical: they pin that a proposer cannot move the
randomness by choosing ledger contents, that a single withholding cannot steer
the outcome (and that the last-revealer choice is bounded, not a re-roll), and
that the committed beacon is byte-for-byte canonical and NodeID-ordered. The
complete, self-contained executable fixtures — fixed `network_id` (the real
32-byte network id), `slot`, the canonical `LedgerHeader`-hash anchor, a
deterministic NodeID-ordered contributor set, and expected digests — are
provided in the companion `contents/cap-0089` folder, alongside the RFC 9381
vectors baked into PR #5409. The RFC-level cryptographic keys and proofs
themselves are the PR #5409 harness's domain; the companion fixtures pin the
*protocol-level* derivations (transcript, aggregation order, beacon, sub-seeds)
with real digests that gen_vectors.py reproduces byte-for-byte.

## Implementation

The cryptographic building block is implemented and under review in
[stellar-core #5409](https://github.com/stellar/stellar-core/pull/5409)
(`ECVRF-EDWARDS25519-SHA512-TAI`, RFC 9381, in `src/rust/src/vrf.rs`, exposed
through the existing Rust bridge). It ships:

* RFC 9381 test vectors (prove + verify);
* canonical-point enforcement (`string_to_point` decompress/recompress round
  trip);
* full proof decode before deriving `beta` (rejects non-canonical `s`);
* a fallible encode-to-curve path (no panic across the bridge);
* full secret zeroization of every secret intermediate;
* a C++ smoke test and a Rust C-ABI harness, both green.

The protocol wiring described in this CAP (the `VRFCommit`/`VRFReveal` types
and the `StellarValue` fields `vrfCommits`/`vrfReveals`/`vrfBeaconNext`, the
commit/reveal/aggregation timeline, the three sub-seed consumers) is
intended to land as a separate reviewable increment on top of #5409, per the
scope discipline agreed in review. It will not be wired until this CAP's
timeline is pinned and the XDR is frozen, and until #5409 is actually merged.

## Exit Criteria

The verifiable conditions that must be met before this CAP moves to
`Implemented` and can be included in a protocol release:

- [ ] The `ECVRF-EDWARDS25519-SHA512-TAI` primitive (PR #5409) is merged and the
      RFC 9381 vectors pass in the core build.
- [ ] The XDR change in this CAP (`VRFCommit`/`VRFReveal` and the
      `StellarValue` fields `vrfCommits`/`vrfReveals`/`vrfBeaconNext`, gated on
      `VRF_RANDOMNESS`) is frozen and accepted by the protocol working group.
- [ ] Adversarial conformance vectors V1–V8 (Section "Test Cases") are
      implemented and passing in a deterministic test harness, including the
      fixed transcript fixtures in `contents/cap-0089`.
- [ ] Nomination priority derives from `subseed(0x02)` of the shared beacon,
      while Soroban PRNG and apply order derive from `subseed(0x03)` and
      `subseed(0x04)`; all three paths pass a round-trip determinism test across
      multiple nodes.
- [ ] The feature has been exercised on a test network with Horizon and RPC up
      and reflecting the change, and `LedgerCloseMeta`s captured from new tests
      pass downstream ingestion test cases.
- [ ] V1 (prior-ledger grinding), V2 (single-contribution withholding), and V8
      (transcript/beacon mutation) demonstrably fail closed on a live consensus
      run, not only in unit tests.
