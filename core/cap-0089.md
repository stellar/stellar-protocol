## Simple Summary

Introduce new host functions that are analgous to the existing `require_auth[_for_args]` functions, but disallow invoker auth.

## Working Group

As specified in the Preamble.

## Motivation

The built-in authorization mechanism in Soroban supports invoker authorization out of the box: if authorization is required from an address that has invoked a given function, then the authorization is automatically considered a success. In overwhelming majority of the cases, this is the desired behavior: if a contract calls another contract, it implicitly authorizes the callee. A typical example of this is transferring tokens from the current contract: the contract can just call `token.transfer` without any additional signatures, and the call itself is considered to be authorized.

Nevertheless, there are scenarios where the default invoker authorization is not desired. The main motivational example for this is custom account implementation: if an account contract calls `require_auth` for an address, it might have an intention to explicitly delegate authorization to that address (see [CAP-0071-01](./cap-0071-01.md) for more details on delegation implementation). In the case of delegation, if the delegate tries to require authorization from its caller via `require_auth` (e.g. due to mis-configuration), then the authorization would incorrectly succeed because of the default invoker authorization behavior. This scenario allows performing custom account authorization without any externally provided signatures involved, so anyone could authorize actions on behalf on the account and thus bypass the intended logic entirely.

Identifying the delegation loop scenarios like the one described above is currently not always possible, e.g. in case of combining [CAP-0071](./cap-0071-01.md) built-in delegation with delegation based on `require_auth`. In order to address this particular issue, as well as any other potential scenarios where explicit authorization is desired, we introduce new host functions that allow developers to explicitly opt-out of invoker authorization, and thus solving the problem for any delegation loop scenarios at once.

Note, that implementing delegation chains *only* via CAP-0071 `delegate_auth` mechanism is another way to avoid the issues described above (as `delegate_auth` chains do not allow invoker authorization). However, this CAP still has its own role in supporting the legacy delegation implementations, as well as potentially addressing the new use cases that do not exist yet.

## Abstract

Two new host functions are introduced: `require_auth_for_args_no_invoker` and `require_auth_no_invoker`. They behave in exactly the same ways as the respective existing functions (`require_auth_for_args` and `require_auth`), except that they do not execute any logic related to invoker authorization.

### Semantics

#### New host functions

`require_auth_for_args_no_invoker` requires authorization from `address` for a call of the current contract function with the provided `args`. It works exactly like `require_auth_for_args`, but disallows invoker authorization entirely. Thus the only way to satisfy the authorization is to have it explicitly provided in a `SorobanAuthorizationEntry` attached to the transaction.

`require_auth_no_invoker` requires authorization from `address` for a call of the current contract function with its call arguments. It works exactly like `require_auth`, but disallows invoker authorization entirely. Thus the only way to satisfy the authorization is to have it explicitly provided in a `SorobanAuthorizationEntry` attached to the transaction.

## Design Rationale

### New host functions vs disabling invoker authorization in `__check_auth`

An alternative solution to the specific problem described in the Motivation section would be to modify the existing `require_auth_for_args` and `require_auth` host functions to optionally disallow invoker authorization when they are called from the `__check_auth` contract function. 

The downside of this approach is that it would modify the existing protocol semantics, so there is no guarantee that an existing contract where this behavior is intentional would not be broken by the change. It is also a solution to a very specific problem, whereas introducing new host functions allows developers to opt-out of invoker authorization in arbitrary scenarios, which may not involve `__check_auth` at all.

Thus the proposed solution is both more general, and also does not risk breaking existing contracts. The main downside of it is that the developers would need to update their contracts. The trade-off is considered acceptable here given the increased flexibility and safety it provides.
