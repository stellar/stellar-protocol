## Simple Summary

Today, every piece of per-ledger randomness in Stellar derives from the last
closed ledger (LCL) hash. Because the quorum leader influences which ledger
closes and what it contains, that same leader can bias three protocol-critical
outputs that are supposed to be unpredictable: SCP nomination priority, the
Soroban PRNG seed, and the order in which transactions apply.

This CAP replaces that leader-influencable randomness with a **Verifiable
Random Function (VRF)** — specifically `ECVRF-EDWARDS25519-SHA512-TAI` (RFC
9381), whose building block has already landed in
[#5409](https://github.com/stellar/stellar-core/pull/5409). A VRF binds each
derived value to a private key in a way that is **pseudorandom** (nobody can
predict it in advance), **publicly verifiable** (any node can confirm the
producer held the claimed key), and **uniquely committed** (a producer cannot
produce two valid outputs for one input). Slotted into the right place in the
consensus timeline, this removes the "grinding" attack surface of the current
design.

## Motivation

### The problem: leader-influencable randomness

The Stellar protocol currently derives all per-ledger randomness from the hash
of the last closed ledger (the LCL). Concretely:

| Consumer | Call site | Today |
|---|---|---|
| Nomination priority | `SCPDriver::computeHashNode` | `hashHelper(slot, prev, round, nodeID)` — the LCL hash leaks into priority |
| Soroban PRNG | `LedgerManagerImpl` (`sorobanBasePrngSeed`) | derived from `txSet.getContentsHash()` |
| Transaction apply order | `TxSetFrame` (`ApplyTxSorter`) | deterministic shuffle keyed off `getContentsHash()` |

Because the LCL hash is determined *before* the next nomination round begins,
and because the quorum leader influences *which* ledger closes, a leader can
search for a favorable LCL hash before committing — a classical **grinding
attack**. The consequence is that a single actor gets measurable control over
values the protocol presents as unpredictable.

### Why a VRF, and what it buys

A VRF evaluation `beta = VRF_prove(sk, alpha)` satisfies:

- **Pseudorandomness** — for anyone without `sk`, `beta` is indistinguishable
  from random until it is revealed.
- **Uniqueness** — for a fixed `(sk, alpha)` there is at most one valid `beta`;
  the producer cannot produce two.
- **Verifiability** — with `pk`, `alpha`, `beta`, and the proof `pi`, anyone
  can check `beta` was honestly derived (RFC 9381, §3).

These properties directly negate the three failure modes above. But — and this
is the central design point of this CAP — **the privacy properties of a VRF do
not, by themselves, prevent a producer from choosing among many alternative
`alpha` inputs.** If the input binds to data the producer controls at
commitment time, the producer can evaluate many candidate inputs and select a
favorable output, reintroducing grinding at a higher layer. The VRF is the
primitive; the protocol is what must guarantee **no meaningful choice among
randomness outcomes**. This CAP is written to make that property concrete and
verifiable, and it is the primary acceptance criterion for the migration.

### Goals Alignment

This CAP is aligned with the following Stellar Network Goals:

* The Stellar Network should run at scale and at low cost to all participants
  of the network — this hardening incurs sub-millisecond cost and no new key
  infrastructure.
* The Stellar Network should be a highly secure and reliable public network —
  removing a known leader-influence vector strengthens fairness and
  cryptographic hygiene for a consensus-critical system.

## Abstract

This CAP introduces protocol-level, VRF-derived randomness. A fixed **canonical
transcript** is built from the *already-finalized* previous ledger (whose
contents nobody can change), and each validator self-selects as a candidate
leader by evaluating a domain-separated VRF over that transcript. The winning
candidate's VRF output (its `beta`) becomes a single verifiable beacon for the
next ledger, from which **independent, labeled sub-seeds** are derived for
nomination priority, the Soroban PRNG, and transaction apply order. Because the
transcript is fixed before the object being randomized is chosen, the producer
obtains **zero choice** among randomness outcomes — eliminating both the
grinding attack and post-compute withholding as leverage vectors.

The cryptographic building block (`ECVRF-EDWARDS25519-SHA512-TAI`, RFC 9381)
ships upstream in stellar-core PR #5409, complete with RFC 9381 test vectors,
secret zeroization, canonical-point and full-decode enforcement, and a fallible
encode-to-curve path. This CAP depends on that primitive and specifies its
*protocol-level use*: the transcript format, the beacon timeline, the sub-seed
derivation, and the adversarial conformance vectors that prove Stellar's use of
the crypto.

## Specification

### Design overview

The core design moves the entropy *before* the object being randomized, and
makes leadership **self-selected by the VRF** rather than granted by the LCL
hash. The timeline is:

1. **Fixed prior context.** Ledger `N` is finalized and externalized. Its
   `LedgerHeader`, `txSetContentsHash`, `ledgerSeq`, and close time are all
   immutable and known to every node.

2. **Canonical transcript.** Each validator builds the same canonical
   transcript `T(N)` from that fixed prior context (Section "Canonical
   transcript" below). Since `N` is already externalized, `T(N)` is the same
   byte-for-byte for every honest validator, and no single actor can alter it.

3. **VRF leader election.** Each validator that wishes to lead slot `N+1`
   evaluates `candidate = VRF_prove(sk_v, T(N))` and submits the candidate
   value (beta + proof) as part of its SCP nomination. The nomination priority
   of each candidate is derived deterministically from `beta_v` (Section
   "Sub-seed derivation"). Because `T(N)` is fixed, `beta_v` is unpredictable
   to everyone including the validator itself until committed — so no validator
   can bias the priority toward itself, and no validator can re-roll.

4. **Beacon commitment.** The candidate whose `beta` carries the optimal
   priority wins the slot. Its `beta` (the **beacon**) is committed in the
   `StellarValue` of slot `N+1` (Section "XDR changes") and verified by every
   node against the winner's public key, `T(N)`, and the recovered proof.

5. **Sub-seed derivation.** Each of the three consumers derives an independent,
   labeled sub-seed from the single beacon through a domain-separated PRF
   (Section "Sub-seed derivation"), so a favorable value for one purpose cannot
   be traded against another.

The dependency cycle identified in review — "leader for `N+1` is defined by
nomination, while that same leader's beta feeds `N+1` priority" — is resolved
because the beacon is computed over the *fixed prior ledger* `N`, **before**
nomination for `N+1` begins. There is no feedback from the randomized object
into its own entropy source.

### Canonical transcript

The transcript is the concatenation of fixed, canonicalized fields of the prior
finalized ledger `N`:

```
T(N) = "stellar-vrf" | 0x01 | network_id | slot | purpose | prior_context(N)
```

Where:

| Component | Meaning | Length / type |
|---|---|---|
| `"stellar-vrf"` | ASCII static label | 11 bytes |
| `0x01` | transcript version byte (bump on any breaking change) | 1 byte |
| `network_id` | `[0x00] || 32-byte PASS_PHRASE hash`, the Stellar network id | 33 bytes |
| `slot` | `ledgerSeq` of the ledger being generated (`N+1`), big-endian | 4 bytes |
| `purpose` | single-purpose label (see below) | 1 byte |
| `prior_context(N)` | fixed hash of externalized ledger `N` (see below) | 32 bytes |

The `purpose` byte is one of:

| Value | Purpose |
|---|---|
| `0x01` | leader-election (nomination priority) |
| `0x02` | Soroban PRNG seed |
| `0x03` | transaction apply order |

Note that the leader-election evaluation uses `purpose = 0x01`; the remaining
two purposes are *derived* from the winning beacon rather than independently
evaluated (Section "Sub-seed derivation"), so they are listed here only to keep
the label namespace canonical and unambiguous.

`prior_context(N)` is the canonical hash of the externalized ledger `N`:

```
prior_context(N) = H( ledgerHeaderHash(N) || txSetContentsHash(N) )
```

where `ledgerHeaderHash(N)` is the canonical `LedgerHeader` hash of ledger `N`
and `txSetContentsHash(N)` is the canonical contents hash of the `TransactionSet`
externalized for `N`. Both are fixed the moment `N` is externalized. Binding to
both fields prevents a leader from reusing a previously revealed beacon across
slots and ties the beacon to the exact state being advanced.

### Sub-seed derivation

The winner's `beta` is a single 64-byte VRF output. We never consume it
directly; instead each consumer derives an independent 32-byte sub-seed through a
domain-separated keyed derivation, preventing cross-purpose reuse:

```
subseed(purpose) = SHA-512( "stellar-vrf/sub" | 0x01 | network_id | slot | purpose | beta )[0:32]
```

Using independent labels means a validator that happens to obtain a favorable
outcome for one purpose cannot use that same outcome to steer another. Each
consumer then uses its sub-seed exactly where today's LCL-derived value is used:

| Consumer | Uses `subseed(0x02)` / `subseed(0x03)` |
|---|---|
| Soroban PRNG | `sorobanBasePrngSeed = subseed(0x02)` |
| Apply order | shuffle key = `SHA-256(subseed(0x03) ‖ txHash)` |

For nomination priority, the leader-election `beta` itself (`purpose = 0x01`)
is mixed into `computeHashNode` so that the pseudorandom priority is fixed for
the slot but unpredictable in advance:
`priority = hashHelper(slot, prev, round, nodeID, beta_v)`.

The `GeneralizedTransactionSet` itself is **unchanged** in this CAP. The beacon
is carried in `StellarValue` (the consensus-critical value), and the sub-seeds
are derived deterministically by every node from the winner's committed `beta`
and the fixed prior transcript. This keeps the `TransactionSetV1.phases`
structure untouched, avoids inflating every transaction set with 144 bytes of
per-vote VRF material, and keeps verification to a single point: the
`StellarValue.ext` `vrfValue` arm, checked once during consensus before the set
is externalized.

### Semantics

**Nomination.** When a validator nominates a candidate value for slot `N+1`, it
attaches its self-selected `vrfValue` (beta, proof, nodeID, transcript hash, and
its node signature) computed over `T(N)` with `purpose = 0x01`. Other nodes
prefer candidates whose `beta` yields the optimal `prio = hashHelper(...,
beta)` per the existing nomination-priority machinery, but now keyed to an
unpredictable, un-re-rollable value.

**Verification.** A node that receives a candidate `vrfValue` for slot `N+1`
MUST, before preferring or externalizing that value:

1. Recompute `T(N)` from the fixed externalized ledger `N` and check
   `H(T(N)) == vrfTranscriptHash`.
2. Verify the VRF proof with the candidate node's on-network public key:
   `VRF_verify(pk_v, T(N), beta, pi)` returns valid and recovers `beta`.
3. Confirm `vrfSlot == N+1` and `vrfNodeID` matches the candidate.

Any candidate failing these checks is treated as invalid and not preferred.
Because `T(N)` is fixed, two validators evaluating the same transcript derive
the same disjoint-set of candidate priorities, and each candidate's `beta` is
deterministic given the key the validator held at `N`.

**Soroban PRNG and apply order.** Once the winning `beta` is committed for
slot `N+1`, every node derives `subseed(0x02)` and `subseed(0x03)` from it and
uses them exactly where it uses the LCL-derived values today. The change is
localized to the three seed consumers; the surrounding consensus, fee, and
execution machinery is untouched in this CAP.

### Non-goals

This CAP does **not** change transaction inclusion or censorship properties:
leaders still choose which transactions are included (a deliberate, documented
case in issue #4388). It also does not introduce a new key type — the existing
Ed25519 node key is reused as the VRF key, keeping StrKey formats and tooling
unchanged. Cross-validator key rotation and slashing are out of scope for this
CAP and flagged for follow-up.

## Design Rationale

### Why the transcript is bound to the prior ledger, not the current one

The single most important decision is where the entropy comes from. Binding the
VRF input to the *current* candidate's own transaction-set contents — as the
original issue sketch (`alpha = lcl.hash ‖ ledgerSeq ‖ txSetContentsHash`)
suggested — lets the proposer vary those contents before committing and grind
for a favorable output. Binding the input instead to the **already-finalized
prior ledger** removes that freedom entirely: `T(N)` is byte-for-byte fixed
before nomination for `N+1` begins, so a validator has exactly one legal input
per slot and per purpose. This directly satisfies the review criterion "a
proposer should not get meaningful choice among randomness outcomes."

The residual attack — a validator that computes a favorable `beta` and then
**withholds** it — is bounded by the FBA model itself: withholding only wastes
that validator's candidate slot, and SCP timeouts plus multiple nominees per
round mean the network advances regardless. We do not claim to eliminate
withholding (no single-slot-adversary scheme can); we eliminate its *leverage*,
since a withheld value simply selects another candidate's already-fixed
beacon.

### Why VRF leader election instead of a round-robin or hash leader

Using the VRF output to *self-select* leadership (rather than deriving a leader
from the LCL hash) means the priority is pseudorandom, un-re-rollable, and
publicly attributable to a specific on-network key. Alternatives — rotating
leaders by `nodeID` order or by LCL-hash — either introduce the exact
predictability/bias this CAP removes or select a leader before any randomness
is committed. VRF self-selection also composes naturally with the existing
nomination-priority machinery: it simply replaces the entropy input to
`computeHashNode`.

### Why a single beacon with labeled sub-seeds

Reusing one `beta` directly across nomination, the PRNG, and apply order would
let a favorable PRNG outcome double as a favorable order outcome. Deriving
independent, labeled sub-seeds bounds each purpose to its own 32 bytes of
entropy, so outcomes across purposes are independent. This is the same
domain-separation discipline recommended in review and used by the RFC's own
ciphersuite labels, and it makes the "purpose separation" conformance vector
trivially checkable.

### Related work

VRF-based randomness (and VRF leader election) is well established in
consensus literature and production systems — Algorand's sortition, the Ouroboros
family, and RFC 9381's own design all bind a pseudorandom value to a key and
make it verifiable. This CAP is deliberately conservative: it reuses the
network's existing Ed25519 keys, keeps the three consumers localized, and lands
the crypto as a separately-reviewed primitive first (PR #5409), so the protocol
change is small and auditable.

## Protocol Upgrade Transition

This is a protocol upgrade and ships behind a new protocol version in
`LedgerUpgradeType::LEDGER_UPGRADE_VERSION`. Under the legacy protocol version,
all existing `StellarValue` arms and the LCL-derived randomness are unchanged.

During transition, both old and new `StellarValueType` arms must be parseable.
Nodes on the new protocol version verify the `vrfValue` arm; nodes on the old
version ignore unknown arms per the existing "drop unknown steps during
consensus" rule. Because verification only *adds* a check and the sub-seed
derivation is deterministic, a node that has not yet upgraded still derives the
same apply order and PRNG as an upgraded node for an upgraded-format value.

The hard prerequisite before this protocol version ships is the XDR frozen with
this CAP — specifically the `StellarValue.ext` `vrfValue` arm and the
`StellarValueType::STELLAR_VALUE_VRF` enum value. The beacon timeline and
transcript are pinned by this CAP and are not implementation details.

## Backwards Incompatibilities

This CAP changes consensus-visible data (a new `StellarValue` arm and enum
value) and changes the source of per-ledger randomness. It is therefore gated
behind a new protocol version, and:

* Legacy nodes can parse (and ignore) the new `vrfValue` arm.
* The behavior of the three randomness consumers changes only on the new
  protocol version.
* No change to balances, operations, or existing account semantics.

The consequence of a node mis-verifying a `vrfValue` (or a node on the new
version running with a stale transcript) is that it fails to externalize the
invalid candidate — the same failure mode as an invalid `lcValueSignature`
today. This is safe: verification is deterministic and self-consistent, so all
honest nodes on the new version agree.

### Resource Utilization

* **Compute:** one scalar-multiplication VRF evaluation per candidate per slot
  (nominating nodes), and two scalar-multiplications for verification
  (all nodes). Sub-seed derivation is a single SHA-512 per consumer per slot.
  Total additional work is sub-millisecond and negligible versus SCP round time.
* **Memory/bandwidth:** the `vrfValue` arm adds 64 + 80 + (nodeID/signature
  sizes) bytes to a `StellarValue`, carried once per candidate during
  nomination, not per transaction. The `GeneralizedTransactionSet` is
  unchanged.
* **Disk/database:** no new persistent state beyond the value already carried
  in `StellarValue`/`LedgerHeader`.

## Security Concerns

The security argument rests on three properties, each tied to a conformance
vector in the Test Cases section:

1. **No input selection (grinding).** The transcript `T(N)` is fixed by the
   externalized prior ledger, so a validator has exactly one legal VRF input
   per (slot, purpose). *Covered by the* candidate-txset-grinding *vector.*

2. **No post-compute re-roll (withholding has no leverage).** A withheld
   favorable beacon only forfeits that candidate's slot; the network advances
   on another candidate's fixed beacon. *Covered by the* withholding/selective
   abort *vector.*

3. **Independence of purposes (domain separation).** Each consumer derives from
   a labeled sub-seed, so outcomes across purposes are independent. *Covered by
   the* purpose-separation *vector.*

Security does not depend on keeping any value private (the per-slot `beta` is
publicly verifiable after commit), only on **uniqueness** (one legal output per
input) and **fixed transcript** (one legal input per slot). Both are enforced
by the primitive (RFC 9381) and by this CAP's transcript.

A validator's long-term signing key is used as its VRF key, so the key is
exposed to the same threat model as today's Ed25519 signing key. The building
block hardens this with constant-time operations and full secret zeroization
(PR #5409), and no new key-rotation obligation is introduced. Post-quantum
hardening and cross-validator key rotation are explicitly out of scope here.

## Test Cases

The following **adversarial conformance vectors** are required for any
implementation of this CAP. They are designed to prove Stellar's *use* of the
VRF, complementing the RFC 9381 vectors that prove the primitive. Each vector
is a deterministic, executable acceptance test with a fixed transcript,
fixed keys, and a fixed expected outcome.

| # | Vector | Purpose | Expected |
|---|---|---|---|
| V1 | candidate-txset grinding | A proposer varies `txSetContentsHash` (as in the rejected original binding) and observes the beacon for each variant. | All variants must produce the *same* transcript (because `T(N)` ignores an unfinalized current set) and thus the *same* beacon; the vector establishes that varying candidate contents do not move the randomness. |
| V2 | proposer withholding / selective abort | A validator computes a favorable `beta` and withholds it. | The network must externalize using another candidate's fixed beacon; the withheld value must not be selected and must not stall the round. |
| V3 | alternate proposer | A second validator with a different key evaluates the same `T(N)`. | The two beacons differ; each is independently verifiable; the higher-priority one wins deterministically. |
| V4 | cross-network replay | A `vrfValue` committed on a testnet is replayed onto mainnet (or vice versa). | Verification MUST fail because `network_id` differs, so `T(N)` (hence the transcript hash) differs. |
| V5 | cross-slot replay | A beacon for slot `N+1` is replayed against slot `N+2`. | Verification MUST fail because `slot` differs (transcript hash mismatch) and `vrfSlot` ≠ `N+2`. |
| V6 | purpose separation | The same `beta` is consumed by two purposes. | `subseed(0x02)` and `subseed(0x03)` MUST differ, so a favorable outcome for one purpose cannot be reused for another. |
| V7 | malformed proof / wrong key | A `vrfValue` carries a tampered proof or a signature from a key that did not produce `beta`. | Verification MUST reject, and the candidate MUST NOT be externalized. |
| V8 | transcript mutation | Any single byte of `T(N)` (or its `H(T(N))`) is altered. | The transcript hash no longer matches `vrfTranscriptHash`; verification MUST reject. |

V1 and V8 are the most critical: they pin the central property that a proposer
cannot move the randomness by choosing the input, and that the committed
transcript is byte-for-byte canonical. Full vector fixtures (fixed
`network_id`, `slot`, keys, and expected digests) are provided in the companion
`contents/cap-0089` folder of this CAP, alongside the RFC 9381 vectors baked
into PR #5409.

## Implementation

The cryptographic building block is implemented and under review in
[stellar-core #5409](https://github.com/stellar/stellar-core/pull/5409)
(`ECVRF-EDWARDS25519-SHA512-TAI`, RFC 9381, in `src/rust/src/vrf.rs`, exposed
through the existing Rust bridge). It already ships:

* RFC 9381 test vectors (prove + verify);
* canonical-point enforcement (`string_to_point` decompress/recompress round
  trip);
* full proof decode before deriving `beta` (rejects non-canonical `s`);
* a fallible encode-to-curve path (no panic across the bridge);
* full secret zeroization of every secret intermediate;
* a C++ smoke test and a Rust C-ABI harness, both green.

The protocol wiring described in this CAP (the `StellarValue.ext` `vrfValue`
arm, the transcript/beacon timeline, the three sub-seed consumers) is intended
to land as a separate reviewable increment on top of #5409, per the scope
discipline agreed in review. It will not be wired until this CAP's transcript
and timeline are pinned and the XDR is frozen.

## Exit Criteria

The verifiable conditions that must be met before this CAP moves to
`Implemented` and can be included in a protocol release:

- [ ] The `ECVRF-EDWARDS25519-SHA512-TAI` primitive (PR #5409) is merged and the
      RFC 9381 vectors pass in the core build.
- [ ] The XDR changes in this CAP (`StellarValueType::STELLAR_VALUE_VRF` and the
      `StellarValue.ext` `vrfValue` arm) are frozen and accepted by the protocol
      working group.
- [ ] Adversarial conformance vectors V1–V8 (Section "Test Cases") are
      implemented and passing in a deterministic test harness, including the
      fixed transcript fixtures in `contents/cap-0089`.
- [ ] The three consumers (nomination priority, Soroban PRNG, apply order)
      derive from `subseed(0x01/0x02/0x03)` and pass a round-trip determinism
      test across multiple nodes.
- [ ] The feature has been exercised on a test network with Horizon and RPC up
      and reflecting the change, and `LedgerCloseMeta`s captured from new tests
      pass downstream ingestion test cases.
- [ ] V1 (candidate-txset grinding) and V8 (transcript mutation) demonstrably
      fail closed on a live consensus run, not only in unit tests.
