## Simple Summary

Today, every piece of per-ledger randomness in Stellar derives from
**proposer-influencable ledger / transaction-set material** — and there are two
distinct grinding surfaces, not one. SCP nomination priority keys off the last
closed ledger (LCL) hash, while the Soroban PRNG seed and the transaction apply
order are derived from the current `txSet.getContentsHash()`. Because the quorum
leader influences which ledger closes and what it contains, that same leader can
bias three protocol-critical outputs that are supposed to be unpredictable: SCP
nomination priority, the Soroban PRNG seed, and the order in which transactions
apply.

This CAP replaces that leader-influencable randomness with a **single protected
random pulse per closed ledger**, produced by a precommitted Layer-B
randomness-epoch authority from a **Verifiable Random Function (VRF)** /
unique-threshold root — `ECVRF-EDWARDS25519-SHA512-TAI` (RFC 9381), whose building
block is currently proposed in
[#5409](https://github.com/stellar/stellar-core/pull/5409) and is not yet
merged. Rather than let a single self-selected validator pick the entropy
(which reintroduces a leader bias at a higher layer), every ledger's randomness
is a function of its own **already-externalized value bytes**, committed to a
canonical close `C_s` and protected challenge at the CONFIRM→EXTERNALIZE
boundary; a threshold authority reconstructs the one root `R_s`, and the three
consumers derive labeled sub-seeds from it (`KDF(R_s, "PRNG")`,
`KDF(R_s, "APPLY")`, `KDF(R_s, "NOMINATION")`). Because the pulse is bound to the
closing ledger's own externalized bytes — the last input that could change a
protected use — it removes the prior-ledger "grinding" surface of the current
design, prevents any single key holder from re-rolling or predicting the
outcome, and removes the arbitrary leader selection of the entropy source. There
is no dual timing model and no `NO_PULSE`: a missing proof simply means the
random outcome is not yet actionable (apply is stalled), never an alternate
entropy branch.

## Motivation

### The problem: leader-influencable randomness

The Stellar protocol currently derives all per-ledger randomness from
**proposer-influencable ledger / transaction-set material**, across two distinct
surfaces (the LCL hash for nomination, and the current transaction-set contents
hash for Soroban PRNG and apply order). Concretely:

| Consumer | Call site | Today |
|---|---|---|
| Nomination priority | `SCPDriver::computeHashNode` | `hashHelper(slot, prev, round, nodeID)` — the LCL hash leaks into priority |
| Soroban PRNG | `LedgerManagerImpl` (`sorobanBasePrngSeed`) | derived from `txSet.getContentsHash()` |
| Transaction apply order | `TxSetFrame` (`ApplyTxSorter`) | deterministic shuffle keyed off `getContentsHash()` |

Because the LCL hash is determined *before* the next nomination round begins,
and because the quorum leader influences *which* ledger closes, a leader can
search for a favorable LCL hash before committing — a classical **grinding
attack**. The consequence is that a single actor gets measurable control over
values the protocol presents as unpredictable.

### Why a VRF, and why a naive single-leader VRF is not enough

A VRF evaluation `beta = VRF_prove(sk, alpha)` satisfies:

- **Pseudorandomness** — for anyone without `sk`, `beta` is indistinguishable
  from random until it is revealed.
- **Uniqueness** — for a fixed `(sk, alpha)` there is at most one valid `beta`;
  the producer cannot produce two.
- **Verifiability** — with `pk`, `alpha`, `beta`, and the proof `pi`, anyone
  can check `beta` was honestly derived (RFC 9381, §3).

These properties fix the input-selection failure at the *transaction-set* layer.
But a design in which a **single** validator self-selects as leader by
evaluating its own VRF over a transcript leaves four weaknesses that were called
out during review and that this CAP is written to close:

1. **Prior-ledger grinding.** Binding the VRF input to the already-finalized
   ledger `N` is not enough: the proposer closing `N` controls `N`'s
   transaction set and header, can evaluate its own VRF over every candidate
   `T(N)`, and externalize the version yielding a favorable outcome for `N+1`.
   The transcript is fixed only *after* that choice has already been exercised.
2. **Reveal / no-reveal choice.** A key holder can compute `beta` immediately,
   inspect the resulting priority and sub-seeds, and then decide whether to
   reveal it — a "selective-abort" bias even when it cannot re-roll.
3. **Information cycle.** A peer's `beta` only arrives inside its nomination,
   so a remote node cannot observe the priority input before deciding how to
   vote for it.
4. **Composite-candidate ambiguity.** SCP combines accepted nominations into a
   composite value; "the winning candidate's beta" is not well defined when
   multiple values advance.

The central design statement of this CAP is therefore: **the VRF proves a value
is pseudorandom and key-bound, but the *protocol* must guarantee there is no
meaningful choice among randomness outcomes** — not by one producer, and not by
whoever closes the ledger being referenced. We do that with an **aggregate of
many independent contributions, committed and revealed on a strict, fixed
latency**, so no single actor controls enough of the inputs to steer the
outcome. This is the primary acceptance criterion for the migration.

### Goals Alignment

This CAP is aligned with the following Stellar Network Goals:

* The Stellar Network should run at scale and at low cost to all participants
  of the network — this hardening incurs sub-millisecond cost for nominating
  nodes and no new key infrastructure.
* The Stellar Network should be a highly secure and reliable public network —
  removing a known leader-influence vector strengthens fairness and
  cryptographic hygiene for a consensus-critical system.

## Abstract

This CAP introduces protocol-level randomness as a **single pulse per closed
ledger**, produced by a precommitted Layer-B randomness-epoch authority and
derived from a **unique-threshold / verifiable-delayed proof** over the
**already-externalized close**. For each closed ledger there is exactly one
canonical close-lock commitment `C_s = H("CloseLock" || RandomnessCloseInputV1)`
(see `B1`), where `RandomnessCloseInputV1` is the single canonical encoding of
`(network_id, epoch_hash, ledgerSeq, previousLedgerHash, H(value_bytes))` and
`H` is **`SHA-256` defined once in Section "Specification"** (the same `H`
used for every commitment, epoch rule-hash, and labelled KDF in this CAP; it is
never left inferable from a 32-byte width).
`C_s` **is** the domain the threshold authority signs: there is no second,
independently encoded "challenge" preimage — another encoding is another drift
surface, so the primitive evaluates the already-canonical `C_s` directly.
When SCP **externalizes** that exact value bytes and every node has **locally
fully validated** it (the CONFIRM → EXTERNALIZE → `valueExternalized`
boundary), the epoch authority releases a share only for those exact bytes;
any threshold-valid subset reconstructs the identical canonical proof `P_s`, and
the source root `R_s = root(C_s, canonical(P_s))` is derived only after that
proof verifies. There is no dual `R_pre`/`R_post` timing model and no
caller-selected purpose/class/object field: the slot, the predecessor ledger
hash, the committed value bytes, and therefore the challenge are fixed entirely
by canonical state.

Every consumer derives a **labeled sub-seed from that one root** `R_s`:
`PRNG(s) = KDF(R_s, "PRNG")`, `APPLY(s) = KDF(R_s, "APPLY")`, and
`NOMINATION(s+1) = KDF(R_s, "NOMINATION")` replace today's LCL-hash-derived
values. Core blocks randomness-dependent apply until the proof verifies; a
missing proof stalls (UNKNOWN), it never selects another entropy branch and
never falls back to a timeout-derived no-pulse. Because the randomness is a
hash/derivation of the externalized value bytes themselves (the last input that
could change a protected use), no single proposer or key holder can steer any
consumer's outcome, and the Layer-A per-reveal aggregate is retained only as
conformance/evidence for where a per-reveal aggregate's boundary lies.

The cryptographic building block (`ECVRF-EDWARDS25519-SHA512-TAI`, RFC 9381)
ships upstream in stellar-core PR #5409 (currently under review, not merged),
complete with RFC 9381 test vectors, secret zeroization, canonical-point and
full-decode enforcement, and a fallible encode-to-curve path. This CAP depends
on that primitive and specifies its *protocol-level use*: the single-pulse
close-lock commitment, the CONFIRM/EXTERNALIZE release boundary, the labeled
consumer derivation, and the adversarial conformance vectors.

## Specification

### Design overview

The core moves: (a) the entropy source **from the already-externalized object
being randomized** (the last input that could change a protected use), (b)
leadership/priority fairness away from any single self-selected value, and (c)
the entropy into a **single shared pulse per closed ledger** that is immutable
the moment the close is externalized. The randomizing unit is a **closed
ledger** `s` (a ledger whose `StellarValue` has been externalized); its random
pulse is a function of that externalized value only (Section "Layer B:
Randomness Epoch").

For each closed ledger `s`:

1. **Canonical close-lock commitment.** Core derives the single canonical
   commitment `C_s = H("CloseLock" || RandomnessCloseInputV1(in_v1))` from ONE
   close-input contract (B1): `(network_id, epoch_hash, ledgerSeq,
   previousLedgerHash, H(externalized_value_bytes))` — a pure function of
   canonical state: the externalized value bytes, the ledger slot, its real
   predecessor ledger hash, the network id, and the precommitted epoch hash.
   `C_s` is the **only** threshold-signed domain; there is **no** second,
   independently encoded challenge, and **no** caller-selected
   purpose/class/object field, so one closed ledger has exactly one commitment
   and one protected challenge (dnFV6 / dnFWo / dnFWi).
2. **Release boundary (CONFIRM → EXTERNALIZE).** An epoch authority releases a
   share **only** for these exact externalized value bytes, **only** once SCP
   reaches CONFIRM and the value is **locally fully validated**
   (`setConfirmCommit` revalidates the committed value, commit is confirmed, the
   phase becomes `EXTERNALIZE`, Core emits EXTERNALIZE and calls
   `valueExternalized`). It is deliberately **not** released at accepted-commit:
   `mCommit` in PREPARE is not safe-to-act global finality (Core can clear it).
   Shares travel on the authenticated overlay in a dedicated, wire-discriminated
   per-member carrier (the `RandomnessShareV1` message shape defined under
   "Protocol Upgrade Transition"; it never dilates `StellarValue`/`LedgerHeader`);
   any threshold-valid subset reconstructs the identical canonical proof `P_s`.
3. **Proof verification and root derivation.** Only after the proof verifies is
   the source root `R_s = root(C_s, canonical(P_s))` derived — the consumer-facing
   root binds BOTH the canonical close commitment `C_s` and the canonical proof,
   exactly as `RandomnessCloseInputV1`-derived proof/root do (`proof` ≠ `root`,
   dnFVg). Before the boundary, or below the reconstruction threshold, the
   outcome is **UNKNOWN** — apply is stalled; there is no alternate entropy
   branch and no timeout-derived no-pulse.
4. **Use (same ledger `s`).** Every consumer derives a **labeled sub-seed from
   that one root** `R_s`: `PRNG(s) = KDF(R_s, "PRNG")` (Soroban PRNG),
   `APPLY(s) = KDF(R_s, "APPLY")` (transaction apply order), and
   `NOMINATION(s+1) = KDF(R_s, "NOMINATION")` (the next ledger's nomination
   priority). Core blocks randomness-dependent apply until the proof verifies.

Because the pulse derives from the externalized value bytes themselves — the
last input that can change any protected use — there is no information cycle, no
per-candidate "winning beacon" ambiguity, no dual `R_pre`/`R_post` timing
domain, and every node computes the identical priority basis and identical PRNG
and apply seeds from the same public pulse. No single proposer or key holder can
steer it, and an adversary cannot select transactions against a known late-stage
seed.

### Canonical transcript

> **Framing.** The sections from here through "Beacon aggregation and fallback",
> together with the XDR diff, describe the
> **Layer A per-reveal aggregate** (commit → reveal → aggregate beacon `B(s)`).
> Per the deployment fork (Sections "Protocol Upgrade Transition" and "Status and
> the Layer A / Layer B deployment fork"), Layer A is **conformance/evidence
> only** — it is not the shipped protocol-randomness wire format, and it does
> **not** provide the one-future, subset-neutral, single-pulse guarantee of Layer
> B. The normative deployment path (one pulse per externalized close, one root,
> three labeled consumers) is the single-pulse design in the "Design overview"
> and in "Layer B: Randomness Epoch". The Layer A material below is retained so
> the boundary it does *not* cross is precisely documented and pinned. Where this
> section refers to `subseed(0x02/0x03/0x04)` they are Layer A's evidence labels,
> not the Layer B consumers defined in "Sub-seed derivation".

The per-slot transcript is the concatenation of fixed, canonicalized fields:

```
T_b(s) = "stellar-vrf" | 0x01 | network_id | slot | purpose(=0x01) | prior_context(s)
```

Where:

| Component | Meaning | Length / type |
|---|---|---|
| `"stellar-vrf"` | ASCII static label | 11 bytes |
| `0x01` | transcript version byte (bump on any breaking change) | 1 byte |
| `network_id` | `Application::getNetworkID()` = `SHA-256(network passphrase)` | 32 bytes |
| `slot` | `ledgerSeq` of the ledger being generated (`s`), big-endian | 4 bytes |
| `purpose` | single-purpose label (see below) | 1 byte |
| `prior_context(s)` | canonical hash of the anchor ledger `s-3` (below) | 32 bytes |

Crucially, `network_id` here is the **existing** 32-byte Stellar network id
exactly as produced by `Application::getNetworkID()` — `SHA-256` of the network
passphrase, with no prefix — so transcripts built by any implementation match
the values derived from the standard API. It is **not** `0x00`-prefixed or
otherwise re-encoded.

Only **one** transcript is ever *proved* and committed per slot: the beacon
transcript `T_b(s)`, whose `purpose` byte is the dedicated **beacon purpose**
`0x01`. The consumers never prove a separate transcript — they each derive a
local, domain-separated **sub-seed** from the single beacon `B(s)` through
sub-seed purpose labels (below). This resolves any "unlabeled contribution"
ambiguity: there is exactly one commit/reveal/beacon per validator per slot, and
it proves `T_b(s)` (purpose `0x01`); the three consumers carry no extra
contribution and no extra proof.

The `purpose` byte of `T_b(s)` is:

| Value | Purpose |
|---|---|
| `0x01` | beacon proof (the single proved contribution per slot) |

And the **sub-seed** purpose labels used to derive the three consumer values are:

| Label | Consumer |
|---|---|
| `0x02` | leader / nomination-priority fairness |
| `0x03` | Soroban PRNG seed |
| `0x04` | transaction apply order |

`prior_context(s)` is exactly the existing canonical **`LedgerHeader` hash** of
ledger `s-3`:

```
prior_context(s) = LedgerHeaderHash(s-3)
```

where `LedgerHeaderHash(s-3)` is the canonical 32-byte `LedgerHeader` hash that
is already computed, stored, and cross-referenced throughout Stellar's ledger
history for ledger `s-3` (the `prevHash` chaining the following ledger). It is
used **directly** and is **not** hashed a second time — this avoids any ambiguity
between hashing a serialized header once versus hashing an already-computed
header hash. `s-3` is finalized before the commit phase for slot `s` begins.
Anchoring two ledgers further back than the commit phase guarantees the
transcript is frozen before any proposer could re-roll it while choosing what
to commit or reveal.

### Commit and reveal

Commits and reveals must be **consensus-bound and replayable** so that every
node (including one doing history/catchup replay) derives the identical beacon
for slot `s` and accepts or rejects the same `StellarValue`. The commit set is
therefore part of the consensus-visible value, not ephemeral SCP gossip:

* **Contributor set (deterministic, from consensus data).** The eligible
  contributors for slot `s` are exactly the validators whose authenticated
  commitments appear in `StellarValue(s-2).vrfCommits` — i.e. `Q` is read
  **from the consensus-visible value itself**, not derived from observed SCP
  envelopes (which can differ across nodes and omit non-signing histories).
  Each `VRFCommit` authenticates its `nodeID` with an Ed25519 signature over
  `"stellar-vrf/commit" | 0x01 | network_id | slot | commitHash` using that
  validator's existing NodeID key, so an entry attributed to an arbitrary node
  cannot inflate `Q` without that node's key. `Q` is therefore the same,
  authenticated, consensus-final set on every node; there is no per-node
  "configured threshold" and no ambiguity about who contributes.
* **Commit (ledger `s-2`).** Each contributor `v` computes
  `C_v = SHA-256(beta_v)` and the commit set
  `commit_set(s) = { (NodeID_v, C_v, sig_v) }` is recorded **in the externalized
  `StellarValue(s-2)`** (Section "XDR changes", `vrfCommits`). Because it is
  part of the consensus value, catchup nodes replay the exact same commit set.
  The `C_v` are hiding, so `beta_v` stays private until reveal. Commits are
  canonicalized with the contributor set **strictly ascending** by `NodeID`,
  with exactly one entry per contributor.
* **Reveal (ledger `s-1`).** Each contributor reveals `(beta_v, proof_v,
  transcriptHash_v)`. A node MUST accept a reveal iff:
  1. `nodeID_v` is in `commit_set(s)` (a contributor, not an interloper),
  2. it is the only reveal for `nodeID_v` (duplicates MUST be rejected), and
     entries are `NodeID`-strictly-ascending,
  3. `SHA-256(beta_v) == C_v` from the committed set (binding to the value that
     was already consensus-final at `s-2`),
  4. `transcriptHash_v == SHA-256(T_b(s))` (exact equality is a **mandatory**
     validity rule, so a proposer cannot vary this field to grind the header),
  5. `VRF_verify(pk_v, T_b(s), beta_v, proof_v)` succeeds.
  Every node derives the same accept/reject outcome from the committed set and
  the reveals. Accepted reveals are recorded in `StellarValue(s-1).vrfReveals`,
  with the *full* consensus-visible reveal set carried so replays recompute the
  identical beacon.
* **Reveal-set inclusion (deterministic).** The reveal set is the
  consensus-visible `StellarValue(s-1).vrfReveals` vector as authored and then
  composited by SCP. Compositing is defined by CAP-0034's deterministic
  field-selection rule: each `StellarValue` candidate carries its own **complete**
  `vrfCommits` / `vrfReveals` / `vrfBeaconNext` set, and the composite is the
  single value SCP selects for the slot, so the composite's VRF fields are
  **taken verbatim from that selected candidate — never merged, averaged, or
  combined across candidates.** Because SCP's value multiplexing selects the same
  composite on every node (CAP-0034), every node derives the identical
  `vrfReveals` field; there is no node-local merge of reveal subsets and no
  overlay-observation rule. This honesty note is deliberate: Layer A does
  **not** define an observation-derived rule that forces a value author to
  include any reveal it merely saw on its overlay. Such a rule would be
  node-local (two validators or catchup paths can disagree about which reveals
  they observed), which is exactly the non-determinism Layer B removes. Instead,
  a value author's choice of which verified reveals to carry is part of Layer
  A's *bounded last-revealer-choice* limitation (documented in "Layer A: bounds
  and honest framing"); a majority-colluding set can withhold its own reveals,
  and the threshold-reconstruction case is stated in Non-goals and future work,
  not solved here. Layer B is where subset choice disappears entirely.
* **Aggregation (close of `s-1`).** `B(s)` is derived from the accepted
  reveals (below) and written into `StellarValue(s-1).vrfBeaconNext`.

Only reveals from the committed contributor set that pass all five checks are
aggregated. Everything needed to reconstruct `B(s)` deterministically — the
commit set (`s-2`), the reveals (`s-1`), and the canonical aggregation rule —
is consensus-bound, so a stale or adversarial node cannot observe a different
set and disagree about whether a `StellarValue` is valid.

### Beacon aggregation and fallback

```
B(s) = SHA-256( alpha_1 || alpha_2 || ... || alpha_k )
```

where `alpha_i` are the *verified* `beta_v` from the accepted reveal set,
ordered lexicographically by `NodeID` ascending, and `k` is the number of
accepted reveals. The ordering (and therefore `B(s)`) is deterministic and
identical on every node; it does not depend on the order in which reveals
arrived.

**Threshold rule (deterministic).** Let `Q` be the size of the committed
contributor set for slot `s` (consensus-final at `s-2`). Define the required
threshold as:

```
t = floor(2*Q/3) + 1
```

i.e. **strictly more than two thirds** of the committed contributor set
(`floor(2Q/3)+1 > 2Q/3`). Every node derives the same `t` from the same `Q`.
This is a *majority-of-committed-contributors* acceptance rule chosen to keep
the beacon live under honest-majority partial reveals; it is **not** the FBA
externalization threshold (which is determined by quorum-set topology, not by a
global count), and the CAP does not claim otherwise.

* **Sufficient reveals:** if `k >= t`, `B(s)` is the aggregate above.
* **Insufficient reveals (graceful liveness degradation):** if `k < t` by the
  close of `s-1`, the beacon degrades to status-quo LCL entropy:

  ```
  B(s) = SHA-256( LedgerHeaderHash(s-2) )
  ```

**Fallback threat model (honest).** To force the fallback (`k < t`) an
adversary must prevent contributors from *revealing*, i.e. keep the accepted
reveal count below `t`. That means suppressing `Q - t + 1` reveals. With
`t = floor(2Q/3)+1`, that is roughly `ceil(Q/3)` reveals —**about a one-third
coalition can force the fallback**, which it does by withholding its own
reveals. The CAP does **not** claim this requires quorum control. The honest
property is narrower and precise:

* While `k >= t` holds with an honest-majority contributor set, no single key
  holder can predict or re-roll the committed contribution of any honest node;
  however, when **both** the with/without last-revealer sets meet `t`, the last
  revealer to publish can compute both candidate aggregates and publish the
  preferred one — i.e. **bounded steering** of `B(s)`. The committed `beta_v`
  values cannot be re-rolled, but the last revealer retains a bounded choice
  between the two threshold-satisfying aggregates. This is the acknowledged
  Layer A limitation Layer B removes (subset choice disappears entirely).
* If a (roughly) one-third coalition withholds, the protocol remains live but
  falls back to the LCL-derived value — i.e. entropy degrades to today's
  already-documented adversary-influenced level. The fallback is a **liveness**
  guarantee, not a security guarantee.
* Eliminating the residual that a colluding majority can steer by withholding
  (threshold reconstruction, where any subset recreates a withheld reveal) is
  explicitly out of scope and flagged for follow-up in Non-goals.

### Sub-seed derivation

There is exactly **one** root per closed ledger: the Layer-B source root
`R_s = root(C_s, canonical(P_s))` of the externalized close — a single
canonical function of the close commitment **and** the canonical proof. We
never consume a root directly; each consumer derives an independent 32-byte
sub-seed through a domain-separated keyed derivation from the **single
explicit root** `R_s`, preventing cross-purpose reuse and making the three
consumers of the one pulse unambiguous:

```
KDF(R_s, label) = SHA-256( "KDF" || R_s || label )[0:32]
PRNG(s)         = KDF(R_s, "PRNG")
APPLY(s)        = KDF(R_s, "APPLY")
NOMINATION(s+1) = KDF(R_s, "NOMINATION")
```

Because the root `R_s` is a pure function of the *externalized* value bytes, the
same root is available to and shared by all three consumers; the labeled
`label` distinguishes their sub-seeds, which are pairwise distinct. Using
independent labels means
a favorable outcome for one purpose cannot steer another. Each consumer then
substitutes its sub-seed exactly where today's LCL-derived value is used:

| Consumer | Root | Uses |
|---|---|---|
| Soroban PRNG | `R_s` (the one externalized-close root) | `sorobanBasePrngSeed = KDF(R_s, "PRNG")` |
| Apply order | `R_s` | `SHA-256(KDF(R_s, "APPLY") ‖ txHash)` as the cross-account random seed. Per the CAP-0014 apply-order invariant, transactions are randomized only **between accounts**; transactions of the **same account remain in sequence-number order** (the existing account grouping is unchanged — only its random seed changes, never same-account ordering). |
| Nomination priority | `R_s` (for the *next* ledger) | `hashHelper(..., KDF(R_s, "NOMINATION"))` replaces the LCL-hash-derived priority entropy for slot `s+1` |

Because `R_s` derives from the externalized value bytes themselves — the last
input that can change the protected use, locked at CONFIRM/EXTERNALIZE — every
consumer's entropy is sealed by the same canonical close, no single nominee gains
a priority or PRNG advantage from its own contribution, and no ambiguity arises
when SCP combines nominations into a composite value. There is no dual
`R_pre`/`R_post`, no separate nomination path, and no caller-selected
purpose/class/object: the one canonical challenge is exactly
`C_s = H("CloseLock" || RandomnessCloseInputV1(in_v1))` (B1) — there is no
second independently encoded preimage.

The unavailable-pre-lock property is **not** a claim that the value bytes do not
exist before the lock — a proposer can compute any *candidate* externalized value
early. It is the **S2 fault-model / source-admission property** enforced by the
Layer-B `RandomnessSource`: no complete valid proof, and therefore no root,
exists for an event before its lock witness is **canonically admitted** at the
CONFIRM/EXTERNALIZE boundary (see "Layer B"). Hash-binding to the exact
externalized value bytes fixes the protected object, but the admission boundary,
not any causal nonexistence claim, is the secrecy mechanism. A threshold
authority cannot pre-sign future rounds, because it releases a share only for the
exact boundary-admitted value bytes.

`vrfCommits` carries the hiding commit set for slot `L+2` (published during
ledger `L`); `vrfReveals` carries the verified reveals for slot `L+1`; and
`vrfBeaconNext` is the resulting 32-byte aggregate `B(L+1)`. All three are
`Hash`/`opaque[64]`/`opaque[80]` of **exact** width — no variable-length
`opaque<...>` — so a malformed or truncated value cannot be encoded, and the
`Hash` type (`opaque Hash[32]` in `Stellar-types.x`) matches the `SHA-256`
width used throughout this CAP.

`VRFCommit.sig` is an Ed25519 signature by `nodeID`'s existing NodeID key over
`"stellar-vrf/commit" | 0x01 | network_id | slot | commitHash`, so a value
author cannot inject a commit attributed to a node that never committed (which
would inflate `Q` and force fallback); the signature is verified before the
entry can contribute to `Q`. Both vectors are **bounded** by the named protocol
cap `MAX_VRF_CONTRIBUTORS = 100`, and a value whose vector exceeds the cap, that
is not strictly `NodeID`-ascending, or that contains a duplicate `NodeID` is
rejected **before** any per-reveal cryptographic verification — so an oversized
or malformed candidate cannot force unbounded bandwidth, allocation, or
verification work.

Because the commit set and reveals are consensus-visible and replayable, a node
doing history/catchup replay reconstructs the exact same commit set, reveals,
and aggregate `B(L+1)` that the original close derived — there is no hidden
per-node local state that could make two nodes disagree on whether a
`StellarValue` is valid.

The `GeneralizedTransactionSet` itself is **unchanged**. The `ext` union is
**unchanged** (no new arms; the CAP-0088 arms are untouched and remain
selectable). Verification is localized: every node recomputes `B(s)` from the
committed set and accepted reveals (all consensus-visible) and checks it equals
`StellarValue(s-1).vrfBeaconNext` before using it, and non-matching values are
rejected.

**On `#ifdef` vs. a wire discriminant.** The `#ifdef VRF_RANDOMNESS` in this
diff is the *source-tree* gating used by every CAP (including CAP-0088) to keep
the new types and members conditional until the protocol version that emits
them is enabled; it is **not** a run-time wire discriminant. At the wire level,
the presence of these members is a function of the **frozen protocol version**
(split by `LedgerUpgradeType::LEDGER_UPGRADE_VERSION`), exactly as CAP-0088's
members are. The reason they are trailing top-level fields rather than `ext`
arms is deliberately *not* a way to smuggle history: `ext` is a single
discriminated union and each arm is mutually exclusive, so adding a VRF arm
would prevent a VRF-carrying value from also carrying `MS_CLOSE_TIME` — the
orthogonal fields exist precisely so a value can carry both, while old XDR
cannot decode the new protocol-version framing at all (the same strict boundary
CAP-0088 enforces for its new arms). Historical/pre-upgrade values never
serialize the VRF members because they are produced under a protocol version in
which the members are not yet emitted; the version gate, not the preprocessor,
defines what is on the wire.

### Semantics

**Nomination.** A node nominating for slot `s` uses `KDF(R_{s-1}, "NOMINATION")`
— where `R_{s-1}` is the source root of the already-externalized close of ledger
`s-1` — and thereby the priority basis of each candidate. All nodes share the
same `R_{s-1}`, so priorities are deterministic, unpredictable in advance, and
identical across the network for a given `(slot, prev, round, nodeID)`.

**Verification.** Before a node uses a close's randomness (Layer B):
1. Re-derive the canonical close commitment `C_s =
   H("CloseLock" || RandomnessCloseInputV1(in_v1))` from `network_id`,
   `epoch_hash`, `ledgerSeq`, `previousLedgerHash`, and the externalized value
   bytes (B1), and confirm the stored `C_s` matches.
2. Require the close's proof `P_s` to verify against the precommitted epoch
   authority key **for the exact `C_s`** (the pure verifier
   `verify(epoch, C_s, P_s) -> R_s | None`), and require the close to be
   boundary-admitted (CONFIRM + locally fully validated).
3. Derive `R_s = root(C_s, canonical(P_s))` and the three labeled consumers
   `KDF(R_s, "PRNG")`, `KDF(R_s, "APPLY")`, `KDF(R_s, "NOMINATION")`.

**Per-member share carrier (CONFIRM→EXTERNALIZE).** A threshold share must reach
peers as an authenticated, single-use message, not ride the reconstructed proof
(which is a *later* artifact) and not pollute `StellarValue`/`LedgerHeader`
(3917275401). The canonical share transport is a dedicated, wire-discriminated
overlay message, carried by the existing authenticated **`Envelope`/SCP
message stream** used for the EXTERNALIZE fan-out, with no new consensus phase:

```
struct RandomnessShareV1 {
    uint32  protocol_version;      // 1
    Hash    epoch_hash;            // which epoch authority this share belongs to
    uint32  slot;                  // LedgerSeq the close belongs to
    Hash    close_commitment;      // the reconstructed C_s being signed
    uint32  member_index;          // 1..n, the canonical roster index (1:1 key)
    opaque share<64>;              // this member's threshold share for C_s
    Signature envelope_sig;        // Ed25519 signed by the member's EXISTING
                                   // NodeID key -> node-bound, replayable-detected
};
```

The envelope signature binds `(protocol_version, epoch_hash, slot,
close_commitment, member_index, share)`, so a share is **node-attributable**,
**not replayable** across a different close/epoch/slot, and **deduplicated on
the same `(close_commitment, member_index)` key**. Peers collect shares in a
short recombine window keyed by `close_commitment`; on reaching ≥ `threshold`
distinct valid shares for that commitment they run `recover_proof` and then the
pure `verify(epoch, C_s, P_s)`. Because shares ride the existing authenticated
overlay (never a new `StellarValue`/`LedgerHeader` nibble), the wire-compat and
`LedgerCloseMeta` surface is unchanged for Horizon/RPC/SDK consumers
(e6Wbkq's forward-compat note). A share whose `envelope_sig` fails, whose
`epoch_hash`/`slot`/`close_commitment` are out of scope, or that duplicates an
already-counted `(close_commitment, member_index)` is dropped individually and
never wastes the reconstruction window.

The Layer A per-reveal aggregate described earlier is evidence/conformance only
and is not a shipped protocol-randomness wire format (Section "Protocol Upgrade
Transition").

**Soroban PRNG and apply order.** These consumers derive from the one root
`R_s` of the externalized close: `sorobanBasePrngSeed = KDF(R_s, "PRNG")` and the
apply-order shuffle key `SHA-256(KDF(R_s, "APPLY") ‖ txHash)`. What is
unavailable pre-lock is **valid authority for the canonical close** — a complete
verified proof, and therefore the root, exists only after the externalized value
bytes are confirmed (see the CONFIRM / `valueExternalized` release boundary):
bytes may exist early; authoritative proof may not. A proposer therefore cannot
select transactions against a known late-stage seed, and a threshold authority
cannot pre-sign future rounds (it releases a share only for the exact
boundary-admitted value bytes).

### Non-goals

This CAP does **not** change transaction inclusion or censorship properties:
leaders still choose which transactions are included (a deliberate, documented
case in issue #4388). It does not change the identity model — node keys stay in
their existing StrKey formats and tooling unchanged — but it **does not reuse the
Ed25519 consensus node key** for randomness. The VRF layer (Layer A) and the
Layer-B group each require **dedicated, key-separated keys**:

* **Layer A (VRF).** Each validator derives a **dedicated VRF key** and uses it
  **only** to generate and verify the per-ledger **VRF proof / `beta`** — it is
  never a consensus identity. The **`VRFCommit` message is separately authenticated**
  by the validator's existing NodeID key**: each `VRFCommit` carries
  `{ NodeID nodeID; opaque vrfPublicKey[32]; Hash commitHash; Signature signature; }`
  (XDR below) where `signature` is an Ed25519 signature under `nodeID`'s
  consensus NodeID key over `"stellar-vrf/commit" | 0x01 | network_id | slot |
  commitHash | vrfPublicKey`. Exactly as the Layer A checker verifies —
  `Ed25519PublicKey.from_public_bytes(nodeID)` directly — the NodeID key is
  already consensus-recognized; the signature authenticates both that the
  `VRFCommit` came from the asserted contributor **and** the NodeID→VRF-public-key
  mapping, while the dedicated VRF key independently supplies the
  pseudo-random `beta` that is committed (the `commitHash` is over `beta`).

  **Key separation (Copilot this review #7/#2).** PR #5409's `ecvrf_derive_key`
  expands the supplied **32-byte seed** with the *standard, non-domain-separated*
  Ed25519 expansion and yields the corresponding public point, so it does not
  itself mint a separately-announced "distinct VRF keypair". This CAP therefore
  **does not present the derived VRF key as cryptographically independent
  consensus-oblivious key material**. The guarantees it can honestly claim are:

  * the VRF secret is **held only in the VRF primitive** (PR #5409), never
    exported or used to sign consensus messages, so a compromise of the VRF
    output does not expose a signing key and vice-versa (separate *use*, not
    separate *key material*);
  * the `beta` the VRF key produces is committed (`commitHash = SHA-256(beta)`)
    and is **pre-image-unlinkable to the leader transcript** before the slot
    finalizes, which is what prevents leader-table grinding;
  * the **NodeID→VRF-public-key mapping is explicitly committed and
    authenticated**: each `VRFCommit` carries the contributor's `vrfPublicKey`
    (the ECVRF verification key), covered by the NodeID signature, so a
    verifier also authenticates that the beta came from **that** node's expected
    VRF key — a malicious contributor cannot commit+reveal an arbitrary chosen
    `beta`, because the reveal must satisfy `ECVRF_Verify(vrfPublicKey,
    T_b(s), beta, pi)` against the NodeID-authenticated `vrfPublicKey`, not a
    key it simply asserts.

  A `VRFCommit` is therefore the single authenticated registration of the
  NodeID→VRF-public-key binding; no separate `KeyUpdateAnnouncement` or control
  seal is introduced, and the proof is always verified against the
  NodeID-authenticated `vrfPublicKey`.
* **Layer B (threshold group).** The group secret is produced by a DKG under the
  epoch's dedicated group key and committed as the epoch's 32-byte
  `authority/group public key` (Section "The object (inert verification
  material)"); it is separate from every node's Ed25519 key and from the Layer-A
  VRF keys. Component nodes use their existing keys **only** to
  authenticate their DKG/roster membership and commitments, not as the group
  key.

This separation (a) prevents a single-key compromise from simultaneously
subverting consensus identity and the randomness surface, (b) keeps the
`authority_key` a pure public commitment (a 32-byte group public key), verified
by `verify(epoch, C_s, P_s)` against the committed `authority_key` — never
against a reused individual node key. It does not attempt a fully
non-grindable RANDAO-style beacon under
a byzantine-majority adversary: forcing the fallback requires **withholding
only `Q - t + 1 ≈ Q/3` reveals** (the liveness boundary for
`t = floor(2Q/3)+1`), *not* a supermajority and *not* control of consensus.
That withheld-set boundary is a **liveness/availability** property of Layer A,
not a value-selection surface; it is documented explicitly and is part of why
Layer A is framed as a bounded-choice primitive (Section "Boundaries of the
reveal/withholding model"), with subset-neutral one-future neutrality left to
Layer B.

**Cross-layer honesty: the per-reveal aggregate is not subset-neutral.** This
CAP's Layer A primitive (the per-reveal `SHA-256` aggregate) does **not**
eliminate the last-revealer in/out choice — a changed valid reveal subset
changes the aggregate, so participation can still select among a *bounded* set
of roots (Section "Boundaries of the reveal/withholding model"). The CAP never
claims otherwise, and it does **not** present Layer A as satisfying subset
invariance.

**Layer B (subset-invariant protocol randomness) is the deployment target, kept in
`Draft` until the primitive lands.** The exit criterion for protocol randomness is **one-future
neutrality**: each closed ledger has exactly one canonical pulse — one protected
close `C_s`, one challenge, one valid proof, one root `R_s`, or **UNKNOWN**
(stalled apply) — with **no caller-selected `outcome_class` and no `NO_PULSE`**:
an absent proof means the random outcome is simply not yet actionable, never an
alternate the caller may choose and never a timeout-derived no-pulse. This holds
independent of which valid subset reconstructs, whether one controller is split
across `m` NodeIDs, how the overlay delivers messages, how fast the attacker
computes, or which consensus path seals it. That
requires a precommitted **randomness epoch** (fixed group key, Sybil-resistant
membership commitment, threshold, activation ledger — no successor capability)
whose scheduled output is reconstructed the same way from any valid subset — a
threshold / reconstruction primitive (e.g. unique threshold signatures in the
drand/DFINITY sense, a verifiable delayed beacon, or another construction proven
to reconstruct one root) that is **not yet in Stellar's reviewed crypto
pipeline**. Until that prerequisite lands, Layer B stays `Draft`; below the
reconstruction threshold a close is **UNKNOWN** — apply is stalled — and there
is no alternate entropy source and no no-pulse inferred from timeout. Identity, transport, and
compute neutrality plus consumer sealing (Section "Sub-seed derivation") and
consensus separation are explicit acceptance criteria for Layer B, with
adversarial vectors enumerated in "Test Cases" and the executable
`layer_b_model.py` (B1–B4, O1–O3). Cross-validator key rotation and slashing
remain out of scope and flagged for follow-up.

## Design Rationale

### Why the aggregate beacon, not a single self-selected leader

The simplest VRF design — each validator self-selects as leader by evaluating
its own VRF and presenting `beta` inside its nomination — fails the review
criteria on four counts (prior-ledger grinding, reveal/no-reveal bias,
information cycle, and composite-candidate ambiguity). An aggregate beacon
dissolves all four at once:

* **Shared input.** `B(s)` is a single public value consumed by all nodes, so
  there is no per-candidate "winning beacon" and no composite ambiguity.
* **Many contributors.** No single key holder controls `B(s)`; its own reveal
  is one term mixed into `SHA-256` over many. This removes *re-rolling* (a
  committed value cannot be changed) and *prediction* (the aggregate is
  pseudorandom until the reveal set is frozen), and removes the prior-ledger
  grinding surface of a single self-selected leader.
* **Fixed latency.** Commits are frozen at `s-2`, reveals are verified and
  aggregated at `s-1`, and the aggregate is committed at the close of `s-1` —
  before `s` begins, so no information cycle and no feedback into the randomized
  object.

### Boundaries of the reveal/withholding model (honest statement)

The commit/reveal construction removes re-rolling, prediction, and prior-ledger
grinding, and it removes a *withholding* lever in the sense that a contributor
cannot steer the final aggregate toward a favorable value it has already
computed (its own term is one unpredictable input among many). It does **not**,
by itself, eliminate the **last-revealer in/out choice**: a contributor that
reveals last can observe the other published reveals, compute the aggregate
with and without its own `beta_v`, and choose which of the two to leave in the
record, so long as the remaining accepted set still meets the threshold `t`.
Because both candidate outcomes are pseudorandom and unsteerable by that
contributor (it cannot make "beta_v in" favorable to itself — it only decides
whether its own term is present), this is a *bounded* two-outcome choice rather
than a re-roll or a grinding surface; but it is a real residual choice that this
CAP does not claim to remove.

Eliminating it entirely requires a Threshold Randomness construction in which
any subset of contributors can *reconstruct* a withheld contribution — e.g.
Shamir/two-round reconstruction where the beacon is a function of all committed
values even if some reveals are withheld. That construction is explicitly
out of scope for this CAP and flagged for follow-up (Section "Non-goals"). The
conformance vectors pin exactly the properties this CAP does guarantee (no
prior-ledger grinding, no re-roll, no cross-network/slot reuse, purpose
separation) and do not overstate the withholding guarantee.

### Why the transcript anchors to `s-3`, and how grinding is bounded

Binding to "the prior ledger" is insufficient, because whoever closes that
ledger controls its contents. This CAP anchors the transcript to ledger `s-3`,
which is finalized **before** the commit phase at `s-2` — so the anchor itself
cannot be re-rolled while commits are being made, and the `s-2`/`s-1` proposers
cannot select among alternative `T(s)` values. The residual theoretical surface
— an adversary that controls the closure of `s-3` and thus the single anchor —
is bounded by two independent facts: the adversary would have to choose a
favorable anchor *blind*, before the honest contributions are committed or
revealed, and the aggregate over honest contributions is pseudorandom and
unpredictable to it. As long as the honest-majority committed contributor set
keeps revealing (`k >= t`), the adversary cannot steer the beacon. Forcing the
fallback instead means suppressing `Q - t + 1` reveals — with
`t = floor(2Q/3)+1`, roughly a one-third coalition withholding its own reveals
— at which point the protocol stays live on the LCL-derived fallback (see
"Beacon aggregation and fallback"); that is a liveness degradation, not a
grinding surface, and the residual colluding-majority steer is stated in
Non-goals.

### Why the strict commit/reveal latency

The strict two-ahead / one-ahead latency is what makes the hidden-then-verified
flow sound: a reveal must match a commit made before the revealer could know
which reveal would be favorable to itself. This prevents both re-rolling (the
commit binds the value) and post-compute substitution.

### Why an orthogonal top-level field in `StellarValue`

`StellarValue.ext` is a single discriminated union; adding VRF as another arm
would make it mutually exclusive with the CAP-0088 `MS_CLOSE_TIME` arms.
Orthogonal gated fields coexist with every existing `ext` arm, keep the commit
set and reveals consensus-visible and replayable, and use only `Hash`/fixed
`opaque[n]` types matching the `SHA-256` width used throughout this CAP. This
directly addresses the "preserve all already-active semantics" requirement
raised in review.

### Why labeled sub-seeds from one beacon

Reusing one value directly across nomination, the PRNG, and apply order would
let a favorable PRNG outcome double as a favorable order outcome. Deriving
independent, labeled sub-seeds bounds each purpose to its own 32 bytes of
entropy. This is the same domain-separation discipline recommended in review and
used by the RFC's own ciphersuite labels, and it makes the "purpose separation"
conformance vector trivially checkable.

### Related work

Aggregated VRF/delayed-reveal randomness is well established — RANDAO and
drand use commit-reveal aggregation, Algorand and Ouroboros use VRF sortition,
and RFC 9381's ciphersuite labels use domain separation. This CAP is deliberately
conservative: it uses a **dedicated VRF key** per validator derived as a domain-
separated seed (the seed fed to PR #5409's `ecvrf_derive_key` is
`SHA-256("stellar-vrf/v1/derive" | network_id | ed25519_key)` so the VRF scalar
differs from the raw consensus key — the defense is separate *use*, a secret
held only inside the VRF primitive, and a `beta` committed as the pre-image-
unlinkable `commitHash`, not a claim of cryptographically independent key
material), keeps the three consumers
localized, adds a compact, replayable commit/reveal/beacon record to the
consensus value, and lands the crypto as a separately-reviewed primitive first
(PR #5409), so the protocol change is small and auditable.

## Protocol Upgrade Transition

This CAP exposes **one deployment path only**, and it is the Layer-B one-future
construct — the commit→confirm→externalize pipeline over a precommitted
`RandomnessEpoch`. Layer A and the `ECVRF-EDWARDS25519-SHA512-TAI` primitive are
**research evidence only**: they pin the conformance/authority boundary and the
proof/root split, but they carry **no deployable transition** and are **not**
shipped as the protocol-randomness wire format (Section "Status and the Layer A /
Layer B deployment fork"). There is therefore no intermediate trailing-field
`StellarValue` format to migrate through, and no second wire format to replace:
the XDR in this CAP is retained as the conformance/evidence surface and the
reference for what a runtime-decodable, backward-decode-gated extension must look
like, not as the frozen shipping format. This removes the tension between any
"Phase A/B/C below" reading and the deployment fork, and deletes the
intermediate trailing-field compatibility problem instead of spending complexity
fixing it twice.

When the Layer-B deployment gate closes, a runtime-decodable wire format around
the `RandomnessEpoch` interface is frozen and the new protocol version activates
behind `LedgerUpgradeType::LEDGER_UPGRADE_VERSION`. Under the legacy protocol
version, the VRF fields are absent (`#ifdef VRF_RANDOMNESS`) and the
LCL-derived randomness is unchanged. As with CAP-0088, the network flips to the
new version only when a quorum of validators is upgraded; nodes that have not
upgraded cannot externalize a value carrying the new fields and buffer until
their version matches — the same strict version gate (see `core/cap-0088.md`).
No "old node derives the same value from the new format" claim is made: old
nodes cannot interpret the new format at all, correctness is guaranteed by the
version gate.

**Consensus responsibilities are split across the two layers that actually
ship (Core, plus Rust behind the existing bridge).**

* **Core** owns:
  - the **canonical close commitment** derivation
    (`C_s = H("CloseLock" || RandomnessCloseInputV1(in_v1))`, B1) over
    `{network_id, epoch_hash, ledgerSeq, previousLedgerHash,
    H(externalized_value_bytes)}` — `C_s` is the **only** protected challenge:
    slot and the locked object (the externalized `StellarValue` bytes) are
    **derived from canonical consumer-use state**, never caller choices — there
    is **no** caller-selected purpose/class/object field and **no** second,
    independently encoded challenge domain (dnFV6);
  - **epoch activation** (the `RandomnessEpoch` activation/retirement window)
    and the **replayable lock witness** (the CONFIRM certificate);
  - **replay** — catchup/replay years later reconstructs the same event under
    the same bytes.
* **Rust** owns, behind the existing bridge:
  - **proof verification and root derivation** for the threshold one-future
    primitive;
  - the **release boundary**: authority for a protected root is released only
    once SCP reaches **CONFIRM** — `setConfirmCommit` revalidates the committed
    value, commit is confirmed, the phase becomes `EXTERNALIZE`, Core emits the
    EXTERNALIZE statement and calls `valueExternalized`. It is deliberately
    **not** released at accepted-commit: `mCommit` in PREPARE is not safe-to-act
    global finality (Core can clear it while still in PREPARE), so plain
    `acceptedCommit` / `setConfirmPrepared` never authorizes a proof, and the
    externalized value bytes must be **locally fully validated** (dnFVg).

The threshold share is generated in Rust at that CONFIRM→EXTERNALIZE transition,
**before** `emitCurrentStateStatement()` — not at `valueExternalized`, which Core
calls only *after* the EXTERNALIZE statement is emitted (a share generated then
could no longer ride the already-emitted envelope, e6Wbkq). The release hook runs
in the emit path once the slot lock is authoritative (CONFIRM commit revalidated,
value locally fully validated), and the share is carried with that same EXTERNALIZE
propagation, so externalization traffic doubles as share transport — no extra
consensus phase and no pre-finality root oracle. A node may collect peer shares
while it is still converging; it must only *use* the reconstructed root after it
confirms the same canonical close locally. Any valid threshold subset reconstructs
the identical proof/root (the binding witness, not a caller-chosen value,
authorizes it).

The measure to validate the boundary is:

```
first externalize -> local confirm -> proof-ready -> apply
```

Native Core/Rust conformance is the release gate for `Implemented`; the external
harnesses in `contents/cap-0089` may cross-check, but they cannot define protocol
truth.

## Backwards Incompatibilities

This CAP changes consensus-visible data (the single Layer B randomness carrier)
and the source of per-ledger randomness, and is gated behind a new protocol
version. The **shipping** change is a runtime-discriminated Layer-B carrier
around the `RandomnessEpoch` interface; the trailing `#ifdef VRF_RANDOMNESS`
members in the XDR diff are the **conformance/evidence reference, not the
shipping representation** (see "Open compatibility gate" below). Concretely:

* The shipping Layer-B carrier is added as a runtime-discriminated shape (a new
  `StellarValueType` arm, or nested/versioned extension) so that it coexists
  with CAP-0088's `MS_CLOSE_TIME` arms and preserves decoding of legacy values.
* The Layer-A trailing `#ifdef VRF_RANDOMNESS` members in the XDR diff are an
  evidence-only reference: `#ifdef` is a compile-time schema selection, not a
  wire discriminant, so those members do **not** serialize as the shipping
  representation on any protocol version.
* The behavior of the three randomness consumers changes only on the new
  protocol version.
* No change to balances, operations, or existing account semantics.
* The `ext` union (including the CAP-0088 `MS_CLOSE_TIME` arms) is untouched and
  remains fully selectable on the new version.

The consequence of a mis-verified proof (or a node running with stale epoch
state) is **post-externalization only**: the `StellarValue` for the close is
already externalized before any Layer-B proof material is released, so a bad or
missing proof cannot make the node "fail to externalize" that value, and there
is no Layer-A reveal state or beacon. A missing valid proof leaves the close
`UNKNOWN` and **stalls apply**; an invalid proof is `REJECTED` and cannot derive
a root. Neither case retroactively changes the already-externalized
`StellarValue`. Verification is deterministic and self-consistent, so all honest
nodes on the new version agree.

**Open compatibility gate — decided by a backward-decode test (hard review
gate, per Noot's correction).** The trailing `#ifdef VRF_RANDOMNESS` members of
`StellarValue` in the XDR diff of this CAP are the **conformance/evidence
reference**, not the shipping format (Section "Status and the Layer A / Layer B
deployment fork"). A compile-time `#ifdef` is a **schema selection, not a
runtime wire discriminant**: enabling the guard changes the generated struct
shape for the binary, and XDR decoding carries no ledger-version context that
could make trailing fields absent — so a new binary would mis-read legacy bytes.
Because Layer A is evidence-only, Stellar never has to ship that trailing shape
at all: there is no intermediate trailing-field wire format to migrate through
and no second representation to replace.

The **shipping** representation is the single Layer-B runtime wire-discriminated
form around the `RandomnessEpoch` interface, which preserves decoding of the
legacy `StellarValue` while coexisting with CAP-0088's `MS_CLOSE_TIME` arms — a
new `StellarValueType` arm (or a nested/versioned extension shape). The
backward-decode gate, required before `Implemented`, is an executable
conformance test: decode a legacy-format `StellarValue` under the new schema, and
a new value under a schema that knows only the legacy arms; each must be
specified to either succeed or fail, never silently mis-read. This is also the
migration-neutrality requirement of Layer B: catchup/replay years later
reconstructs the same event under the same bytes.

### Resource Utilization

The figures below are for the **Layer-A evidence harness** (commit/reveal/XDR
records that this CAP keeps as a conformance reference). They are **not** the
deployable Layer-B profile.

**Layer A (evidence only):**

* **Compute:** one VRF evaluation per validator per target slot (commit phase)
  and two scalar multiplications for verification per reveal (all nodes),
  amortized across the two-ledger window. Total additional work is
  sub-millisecond and negligible versus SCP round time. *(Legacy prose; the
  evidence harness uses an explicit `SHA-512` for its transcript hash.)*
* **Memory/bandwidth (XDR, per contributor, before vector framing):**
  `NodeID` is 36 bytes (4-byte `PublicKey` union discriminant + 32-byte key).
  A `VRFCommit` is therefore **~132 bytes** (NodeID 36 + `commitHash` 32 +
  `sig` 64), a `VRFReveal` is **~212 bytes** (NodeID 36 + `vrfBeta` 64 +
  `vrfProof` 80 + `transcriptHash` 32), and the aggregate beacon is a fixed
  **32 bytes**. Both vectors are bounded by `MAX_VRF_CONTRIBUTORS = 100`, so
  the worst-case consensus footprint is about
  `(132 + 212) · 100 + 32 ≈ 34.4 KiB` per `StellarValue` — carried per ledger,
  not per transaction. The `GeneralizedTransactionSet` is unchanged.
* **Disk/database:** the consensus-visible commit/reveal/beacon records per
  ledger in `StellarValue` (needed for deterministic replay), plus the bounded
  in-memory reveal bookkeeping during the two-ledger window.

**Layer B (the sole deployable path) is deliberately left unquantified here.**
Its runtime-discriminated wire shape around the `RandomnessEpoch` interface and
its threshold scheme are not yet frozen, and the Layer-B KDF is a single
`SHA-256` (not the Layer-A evidence `SHA-512`). Layer-B compute (threshold
reconstruction + proof verification + one `SHA-256` per labelled consumer per
slot), bandwidth, storage, and added close latency MUST be quantified with real
Core/Rust benchmarks before `Implemented`; the native Core/Rust conformance that
owns each claim (Section "Status and the Layer A / Layer B deployment fork" and
"Backwards Incompatibilities") is where those numbers are pinned.

## Security Concerns

The security argument rests on three properties, each tied to a conformance
vector in the Test Cases section:

1. **No meaningful input selection (grinding is bounded).** The transcript is
   anchored to ledger `s-3`, finalized before the commit phase; the beacon is an
   aggregate over many committed-then-revealed contributions. A proposer cannot
   select among randomness outcomes by choosing `s-3`'s contents (frozen before
   commits), `s-2`'s contents (commits are hidden), or `s-1`'s contents (reveals
   are already committed). *Covered by the prior-ledger grinding vector.*
2. **No re-roll; bounded withdrawal (liveness, not value selection).** A key
   holder cannot re-roll (the commit binds its value) and cannot predict or steer
   the aggregate with its own single contribution. Withholding removes only its
   own term; forcing the fallback requires **withholding only `Q - t + 1 ≈ Q/3`
   reveals** (the liveness boundary for `t = floor(2Q/3)+1`), a *super-majority
   of the contributor set is **not** required, and it is equivalent to the
   consensus-separation boundary documented in "Beacon aggregation and fallback".
   That withheld-set boundary determines **availability**, never which root is
   valid: threshold sizes the *live* set, it cannot pick a different value. As
   stated in the Design Rationale, a *last* revealer retains a bounded in/out
   two-outcome choice; eliminating it (threshold reconstruction / subset
   neutrality) is a Layer B property and is flagged for follow-up. *Covered by
   the single-contribution-withholding vector.*
3. **Independence of purposes (domain separation).** Each consumer derives from
   a labeled sub-seed, so outcomes across purposes are independent. *Covered by
   the purpose-separation vector.*

Security does not depend on keeping any value private after the reveal window
(the beacon is public); it depends on **unique, committed inputs** (one legal
reveal per output, bound by the previously committed hash), **unpredictability
of the aggregate until it is frozen**, and the **deterministic contributor set
and threshold rule**. All three are enforced by the primitive (RFC 9381
uniqueness), by the commit/reveal binding, and by this CAP's consensus-visible,
replayable commit/reveal/aggregation pipeline.

A validator does **not** reuse its consensus Ed25519 signing key for randomness:
it uses a **dedicated VRF key** (a domain-separated seed fed to PR #5409's
`ecvrf_derive_key`, so the VRF scalar differs from the consensus scalar; the
specific derivation is `SHA-256("stellar-vrf/v1/derive" | network_id |
ed25519_key)`), so a compromise of the randomness key cannot subvert
consensus identity, and vice-versa. The derived VRF secret is held only in the
VRF primitive (PR #5409), which hardens it with constant-time operations and
full secret zeroization, and no new key-rotation obligation is introduced: the
VRF key is re-derived deterministically from the same long-term Ed25519 key,
and the raw signing key's existing rotation policy continues to govern both.
Post-quantum hardening and cross-validator VRF key rotation are explicitly out
of scope here.

transcript, fixed public contributions, and a fixed expected outcome.

## Layer B: Randomness Epoch (normative protocol-randomness target)

Layer A of this CAP is the per-reveal ECVRF aggregate; it is a **bounded**
primitive and is explicitly *not* subset-invariant (Sections "Non-goals" and
"Design Rationale"). Protocol randomness that must be **one-future neutral** is
a distinct, normative target — Layer B — whose consumer-facing object is a
single pre-locked randomness authority, **not** an enumeration of revealers.

A consumer of Layer B never asks "which validators did I see reveal?". It asks
only **"does this proof verify under the already-locked epoch key for the
already-locked round?"** That moves membership churn, packet arrival, reveal
inclusion, and contributor ordering below the authority boundary.

The source contract has three independent properties (Noot's separation —
uniqueness alone is not enough, because a threshold group that can evaluate
arbitrary candidate challenges *before* lock could pre-sign predictable
rounds):

```
S1 single binding           : one canonical use -> one close commitment
S2 pre-lock unavailability  : before that close is externalized+validated its
                              root is not computable under the stated fault
                              assumptions
S3 unique resolution        : after lock, every valid proof path -> the same R
```

### The object (inert verification material)

```
RandomnessEpoch E = {
  format_version,                 // canonical identity byte; any rule change
                                  //   MUST bump this and re-derive epoch_hash
  scheme,                         // e.g. "unique-threshold-signature",
                                  // "verifiable-delayed", or future Stellar-native
  authority/group public key,     // consumer-facing verification key
  membership/authority commitment,// who/what can emit proofs for this epoch
                                  //   (Sybil-resistant roster, fixed in advance)
  threshold,                      // fixed threshold of shares to reconstruct
  byzantine_bound f,              // number of byzantine authorities tolerated;
                                  //   MUST satisfy 2*t - n > f (honest
                                  //   intersection across any two t-subsets)
  activation + retirement boundary,
  event -> round mapping,         // (slot, externalized value) -> round r
                                  //   (no caller purpose/class - one pulse per
                                  //   locked close)
  proof verifier,                 // the exact verification rule (incl. proof
                                  //   encoding) bound into the identity
  root derivation,                // proof(E, r) -> exactly one source root
}
```

`byzantine_bound` is a **normative field of the epoch**, committed into
`epoch_hash` and validated at construction: an epoch whose threshold violates
the honest-intersection bound `2*t - n > f` is **invalid and rejected** — with
`2*t - n <= f` two threshold subsets could overlap only in Byzantine members and
therefore mint **two different same-slot proofs**, breaking the one-future law
(dnFV3 / Noot). The model also enforces the **availability bound** `t <= n - f`
at construction (`EpochDescriptor.__init__`): the `f` byzantine members never
present a valid share, so the threshold `t` must be reachable from the `n - f`
honest members alone, otherwise a valid proof can never be produced and the
epoch stalls. Raising `t` past `n - f` (e.g. `t = n` with `f >= 1`) is rejected
fail-closed — the fault model demands that honest members can still meet the
threshold. The model fixes the default at the **largest value satisfying both
bounds**, `f = min(2*t - n - 1, n - t)` for the honest roster, and enforces both
bounds fail-closed (thread eW_rR): when `2*t - n - 1` exceeds the availability
cap `n - t`, the availability bound is binding (e.g. `n = 8, t = 7` yields the
default `f = 1`, valid because `7 <= 8 - 1`). A configured `f` is **preserved**
and then rejected fail-closed if it violates either bound — it is never silently
re-clamped down to hide an unsound epoch (Copilot this review #5). Every proof
issued
under `E` inherits this bound, so validation is part of the epoch identity, not
a live consensus parameter.

The **epoch identity** (`epoch_hash`) is one canonical hash over **all** of the
rules above — `format_version`, `threshold`, `event -> round mapping`, `proof
verifier`, `root derivation`, `authority commitment`, `scheme`, and the
activation/retirement boundary — so that future software can never reinterpret
the same identity under a different meaning. Changing **any one** of those rules
produces a **new** epoch hash (a distinct identity), while every proof issued
under the old epoch keeps **exactly one** interpretation under that old identity.
A verifier therefore never mixes rules across epochs: an event is resolved
against the single canonical epoch whose hash is bound into its close
commitment.


`E` is **inert verification material** — it carries **no successor capability**
(succession lives in ordinary canonical Stellar protocol state, see "Authority /
migration" below) and no delegate, membership-edit, recovery-authority, or
permission field. An old randomness key verifies old events; it does **not**
appoint its successor (Noot's authority separation: a randomness proof must not
become a general permission/delegation chain).

### Authorization timing: the CONFIRM/EXTERNALIZE release boundary

A randomness share must be authorized at the single point where Core can no
longer move the slot to another value: the **CONFIRM → EXTERNALIZE** transition
of the current slot's `StellarValue`. `prepare` is **too early** (a node may
still replace the value or clear its commit), and **accepted-commit
(`mCommit` in PREPARE) is deliberately not authoritative** — it is not
safe-to-act global finality because Core can clear it while still in PREPARE, so
plain `acceptedCommit` / `setConfirmPrepared` never authorizes a proof (dnFVg /
tacticalnoot). The share is released only when:

* SCP reaches **CONFIRM** — `setConfirmCommit` revalidates the committed value,
  commit is confirmed, the phase becomes **EXTERNALIZE**, Core emits the
  EXTERNALIZE statement and calls `valueExternalized`; and
* the externalized value bytes are **locally fully validated** by Core.

The share is bound to the **full serialized `StellarValue`** (its exact
externalized bytes), not to a name that only implies a later externalization
status:

* Core saves the signed envelopes and quorum sets that caused CONFIRM as one
  **replayable lock certificate**; it is the *admission/release provenance* for
  that exact close — the record that the CONFIRM→EXTERNALIZE boundary really
  admitted this value for release. It is **not** an input to the pure proof
  verifier: verification of an accepted proof is the archival, self-contained
  relation over the canonical triple `{epoch, C_s, P_s}` (K3). A future node
  replays the archived `{epoch, C_s, P_s}` (pinned in the closed `LedgerHeader`)
  to re-derive the root — never from local settings, clocks, live network state,
  the lock certificate, or the transport path that carried the shares;
* Core invokes the release hook in the same CONFIRM→EXTERNALIZE emit path,
  **before** `emitCurrentStateStatement()` (the slot lock is already
  authoritative there; `valueExternalized`, which Core calls after the envelope
  is emitted, is too late for the share to ride it, e6Wbkq), and the authorized
  threshold share rides on that same existing **externalize** traffic (and peer
  share collection) — no new network round is introduced;
* every CONFIRM-ratifying quorum carries at least the fixed `threshold` of
  available, valid authority shares, and **every two threshold subsets share an
  honest member who signs only one value per slot** — so the messages already
  required for externalization also reconstruct a unique root. Reconstruction
  overlaps persistence, ledger setup, and source-account prefetch rather than
  creating another serial network phase. If a proof is missing at the first hard
  consumer (fee and sequence processing, which requests the ordered transaction
  phases), the outcome stays `UNKNOWN` and apply is **stalled**; substitute
  entropy is never chosen after the lock, and there is no no-pulse fallback;
* **quorum ↔ roster intersection at activation** — this is TWO distinct
  conditions, not one (Copilot this review). The **roster-only** condition
  `2·t − n > f` proves only that any two size-`t` subsets of the randomness
  roster share an honest member; it says **nothing** about how an FBA quorum
  (a block of quorum-sets, not a numeric committee) relates to the roster. A
  separate, **topology-aware** condition is therefore validated at activation:
  the CAP requires that, against the validator's local FBA quorum topology,
  **every quorum `Q` that can ratify an externalize value for this epoch must
  intersect the roster in at least one honest member** (`∃ m ∈ (Q ∩ roster)` with
  `m` honest, i.e. `Q ∩ honest-roster ≠ ∅`). This is evaluated by Core at epoch
  activation against the actual quorum-sets (not inferred from the numeric
  roster), so a quorum that is **disjoint from the roster** — however the
  (t, n, f) roster bound reads — is a fail-closed activation error and cannot
  fabricate randomness outside the roster. Because the honest members of any two
  threshold subsets overlap, a roster-disjoint quorum cannot observe the
  `t` authoritative shares and therefore cannot reconstruct the canonical proof.
  Both conditions are frozen by the committed epoch identity at activation.

### Event identity: the canonical close-lock

There is no caller-selected `purpose`, `outcome_class`, or object field: the
event identity is a pure function of the externalized close (dnFV6 / dnFWo).
The canonical identity is the close-lock commitment `C_s`, derived from ONE
canonical close-input contract (below, `B1`). `C_s` **is** the domain the
threshold authority signs: there is no second, independently encoded
"challenge" preimage (another encoding is another drift surface); the primitive
evaluates the already-canonical `C_s` directly.

```
H(x)  = SHA-256(x)                 // H is EXACTLY SHA-256, everywhere in this CAP
C_s = H("CloseLock" || RandomnessCloseInputV1(in_v1))
in_v1 = (network_id, epoch_hash, ledgerSeq, previousLedgerHash,
         H(externalized_value_bytes))   // H(value_bytes) = SHA-256(value_bytes)
LockedClose = { epoch_hash, network_id, slot, previousLedgerHash,
                externalized_value_bytes, C_s }
```

`H` is **defined once here and used consistently throughout**: the canonical
close-lock commitment `C_s`, the inner value commitment `H(externalized_value_bytes)`,
the membership-commitment hash, the epoch rule-hash, and every labelled KDF below
all use **`H = SHA-256`** with the exact byte widths shown in Section
"Specification" (a `Hash` / `opaque Hash[32]` is a 32-byte SHA-256 digest).
Because `C_s` is a consensus-critical signed domain (the threshold authority
signs exactly `C_s`), the algorithm is pinned to SHA-256 here rather than left
inferable from a 32-byte width.

The proof `P_s = ThresholdSignature(epoch, C_s)` is a **unique, unforgeable
authenticator for the exact externalized value bytes**, distinct from the root;
it exists **only** after `>= t` valid authority shares for the exact close
reconstruct it (there is no public proof-emission function). The source root
`R_s = root(C_s, canonical(P_s))` is derived **only after** `verify(epoch, C_s,
P_s)` accepts the canonical proof (proof ≠ root, dnFVg). Resolution:

```
REJECTED  : LockedClose integrity, epoch binding, or boundary admission failed
UNKNOWN   : no valid proof yet (pre-boundary, or below the reconstruction
            threshold) -- apply is stalled, never another entropy branch, never
            a timeout-derived no-pulse
ROOT(R_s) : valid unique proof; the verifier derives R_s (the caller never
            supplies it)
```

Every closed ledger has exactly one canonical `C_s` (which **is** the protected
challenge — there is no second, independently encoded preimage) — one pulse per
locked ledger close. There is **no timeout / non-arrival -> NO_PULSE
transition**: in an asynchronous network "I did not receive a proof" can never
establish "no valid proof exists"; absence is observer-relative, and a missing
proof simply means the random outcome is not yet actionable. `REJECTED` is
genuine only when the close fails to be an honest, admitted lock under the
calling epoch.

The epoch authority has **no oracle over candidate witnesses before lock**:
pre-lock unavailability is the **S2 fault-model / source-admission property** of
the epoch primitive (no complete valid proof before the lock witness is
canonically admitted at CONFIRM/EXTERNALIZE), not a claim that the value bytes
are nonexistent early. Consequently an adversarial evaluator cannot pre-sign a
predictable round, and the epoch authority cannot reinterpret the challenge
after the protected object is fixed.

### Protocol law: one future, single and compositional

**Single-event one-future law:**

```
same locked event + any valid delivery / subset / replay / ordering / recovery
path  ->  same verified root R   OR   UNKNOWN (stalled; no root yet)
```

**Compositional one-future law** (Noot's correction — per-round bounded choice
compounds as `2^n` across many draws, so single-round boundedness is *not*
systemic boundedness). Let `R(C_i)` be the authoritative roots reachable after
locked event `C_i`, and `H_n` the set of authoritative histories reachable
across `n` consecutive locked events:

```
for every prefix n:
    |H_n| = 1
    OR the unique history stalls (one or more closes UNKNOWN, apply blocked)
```

**Zero post-lock value-selection sensitivity.** After lock, these variables may
change availability or latency only; none may change the authoritative value:

```
d(authoritative_value)/d(timing)         = 0
d(authoritative_value)/d(route|order)    = 0
d(authoritative_value)/d(identity fanout)= 0
d(authoritative_value)/d(retry)          = 0
d(authoritative_value)/d(threshold path) = 0
d(authoritative_value)/d(recovery path)  = 0
d(authoritative_value)/d(implementation) = 0
```

The same law composes across rounds without carrying hidden optionality forward.

### Three exit laws (Noot's next round — layer-B survival test)

1. **One use -> one event.** Retries, aliases, parallel requests, or equivalent
   event ids must **not** let a consumer lock `N` valid draws and choose one
   after seeing their roots. The close-lock commitment is a pure function of
   canonical state (no caller nonce / retry / alias / class field), so one
   protected use has exactly one id, and duplicate/replay requests collapse to
   the same root.
2. **Earliest-knowledge sealing.** The last input capable of changing the
   protected use must be locked **before the earliest possible valid knowledge
   of the root** — not merely before public broadcast. Faster compute, shorter
   propagation, finer clocks, or earlier observation may change *when* someone
   knows; they create **zero** additional valid action. No wall-clock or
   arrival-time rule may choose the root, the stalled/UNKNOWN state, or the use
   boundary.
3. **Permanent pulse.** Once `pulse_id = H(close, canonical_root)` is
   canonically accepted, later key/suite changes, proof encodings, software
   rewrites, recovery, migration, or archival replay can **never** create a
   second historical pulse.

The three kill questions a conformance test asks (Noot): can anyone create
several equivalent valid events and choose later? can anyone learn the root
while any relevant input is still legally movable? can any future
verifier/migration make a different historical pulse valid? If any answer is
yes, *change the shape* rather than bound the window.

### Why an authority (not an aggregate) is the normative boundary

* **Subset neutrality** falls out of the primitive: a unique threshold output /
  verifiable-delayed output (e.g. drand's regular BLS group signature,
  https://docs.drand.love/docs/cryptography/ ; ICP's chain-key random beacon,
  https://docs.internetcomputer.org/concepts/chain-key-cryptography/ )
  reconstructs the **same** value from any valid subset. Below the reconstruction
  threshold a locked close is simply **UNKNOWN** (never an alternate
  root, never a timeout-derived no-pulse). Threshold governs whether a unique
  proof is *available*, never which root becomes *valid*.
* **No value-bearing fallback.** Withholding reverts `ROOT -> UNKNOWN` (or stays
  `UNKNOWN`), never `ROOT_A -> ROOT_B`. The Layer A LCL fallback does **not**
  exist in Layer B: for a locked close there is exactly one valid root or none
  (stalled apply); there is no `NO_PULSE` outcome by construction.
* **Eligibility / Sybil / identity neutrality.** Contributor eligibility is
  *not* re-derived from self-signed `NodeID`s inside a round. The epoch commits
  the authority and membership **before** any member can influence the target
  round; cloning one controller into `m` NodeIDs at constant consensus influence
  cannot add randomness privilege (a raw identity count is not independent
  security weight). This is precisely why a raw-count membership rule (Layer A)
  is bounded, and why the precommitted Sybil-resistant roster (Layer B) is the
  bar.
* **Observation neutrality.** The verifier is a pure function of
  `predecessor state + proof bytes`; it never asks what this node happened to
  observe. Two nodes with different packet histories but the same locked state
  and any valid proof path verify the same root or both are `UNKNOWN`.
* **Transport neutrality.** Delay, reorder, withholding, partition,
  rebroadcast, or earlier observation change *knowledge time* only:
  `before lock -> no actionable root (pre-lock unavailability)`; `after lock ->
  every valid observer sees UNKNOWN or the same R`.
* **Consumer sealing.** All three consumers (nomination for the next ledger,
  Soroban PRNG, apply order) derive **labeled sub-seeds from the one root**
  `R_s` of the same externalized close: `PRNG(s) = KDF(R_s, "PRNG")`,
  `APPLY(s) = KDF(R_s, "APPLY")`, `NOMINATION(s+1) = KDF(R_s, "NOMINATION")`.
  Because the root is a function of the *externalized* value bytes, a proposer
  cannot select transactions against a known late-stage seed and the authority
  cannot pre-sign future rounds.
* **Consensus separation.** Consensus may attest a pre-existing
  `pulse_id = H(close, canonical_root)`. Quorum path, proposer,
  signer count, message order, or later consensus changes are never inputs to
  the pulse identity.

### Authority / migration (canonical-state succession, permanent pulse)

Succession is **not** a capability of the randomness key. Canonical Stellar
protocol state (protocol upgrade / ledger state) selects and activates the next
`RandomnessEpoch` descriptor; future close commitments then include the new epoch's
hash. An old event remains bound to its old epoch **forever**: a future verifier
with the preserved epoch bytes re-derives the identical root and the identical
`pulse_id` (permanent pulse), and a *rewritten* epoch (new key) is a different
epoch whose event ids differ — it can never re-pin an old event's pulse. No key
rotation, recovery path, re-encoding, or implementation upgrade may reinterpret
an already locked event: exactly the same canonical bytes reconstruct the same
root (or the same pre-locked class). This is what makes catchup/replay years
later observation- and migration-neutral.

### Executable Layer B model (B1–B4)

`contents/cap-0089/layer_b_model.py` is an implementation-neutral, executable
state machine that candidate constructions (threshold-BLS, threshold-VRF,
verifiable-delayed) must implement — the state machine does **not** change to
accommodate whichever primitive arrives first. It is written in the `cryptography`
independent harness style used by the Layer A vectors, with no new Stellar
dependency. Running it (`python layer_b_model.py`) prints PASS/FAIL for:

> **Honest holder vs. attacker surface (this review).** The harness models the
> seeded group secret (`GROUP_SK`) and the signing helpers as the *primitive's
> internal key material* — reachable only from the honest `ThresholdAuthority`
> signing path. It then drives **every** negative-synthesis / pre-lock
> unavailability check (O2, S2, K2) through an `AttackerView` façade that is
> constructed with **only public material** (authority key, roster, membership
> commitment, candidate closes) and exposes **no** shares, seed, `_group_secret`,
> or `_spf_sign`. The evidence asserted is precisely "an attacker interface that
> cannot touch signing material cannot produce an accepted proof or a pre-lock
> root," and the CAP is explicit that the *information-theoretic* `< t`-share
> secrecy itself is the candidate primitive's guarantee (BLS/VUF), which the
> harness documents but does not re-derive.

* **B1 — single close-input pulse (no caller class).** One canonical
  `RandomnessCloseInputV1` binds `{network_id, epoch_hash, ledgerSeq,
  previousLedgerHash, H(externalized_value_bytes)}` — every semantic input able
  to interact with the random result, while **excluding provenance**
  (`lcValueSignature`, proposer NodeID, SCP envelopes/certificate path,
  timestamps, transport metadata). Its canonical wire encoding follows
  Core-native XDR widths (as modeled): the literal contract tag
  `"RandomnessCloseInputV1"`, a `uint32` arm version (currently `1`), then the
  four fixed-width hashes — `network_id`, `epoch_hash`, `previousLedgerHash`,
  and `H(externalized_value_bytes)` — each as a Core `opaque Hash[32]` (a
  **fixed 32 bytes with no length prefix**; the `lp()` length prefix is the
  string-encoding and is **not** the XDR encoding for a fixed `Hash[32]`, so a
  native implementation following the declared XDR widths derives the same
  `C_s`), a `uint32` `ledgerSeq` (Core's `LedgerSeq` XDR type), and the epoch's
  `format_version` as the single canonical identity byte (`uint8`), committed
  separately in `epoch_hash`. The
  close-lock commitment `C_s =
  H("CloseLock" || RandomnessCloseInputV1(in_v1))` **is** the protected
  challenge — the only threshold-signed domain; there is **no** second,
  independently encoded `"Challenge"` preimage (another encoding is another
  drift surface) and **no** caller-selected purpose/class/object field (dnFV6):
  distinct value bytes yield distinct close commitments; one closed ledger has
  exactly one commitment, one challenge, one proof, and one root. Binding
  `previousLedgerHash` also pins state-transition semantics so randomness cannot
  cross a chain/close reorg.
* **B2 — the challenge (C_s) binds the exact externalized value.** Two different
  externalized value bytes yield two different close commitments/challenges, and
  a proof for value A fails against value B; each value resolves only under its
  own boundary-admitted proof.
* **B3 — transport / replay composition.** 601 consecutive closes under **four
  per-event delivery sequences** — `[proof]^601`,
  `[proof]` on even `i` / `[none]` on odd (a `[proof,none]` gap pattern),
  `[proof]` unless `i % 3 == 1` (`[none]` every third),
  and `[proof]` only where `i % 4 in {0,3}` (`[none]` otherwise) — each flushed as
  successive per-event observations. The transient (partial-observation)
  histories differ, and **every** schedule's terminal history is pinned: the four
  registered authoritative-history digests are
  `f3455fda5722e0f3b423d55c604501327edfa5ff8ba6e6a2f07f98e123606754`,
  `9acde5f08f598275c570fc282b3703201beba5678a44b8bdc6ecefada26fc465`,
  `8f8bc77b1a7046d0eeb0183eaaebbc27b8331270c2fb4f49b2dd252c3f25648c`, and
  `2a254ad58cb70edd980a07e38e21f85cdb34ce956518e47f122b52cec7dbc6ed`
  (one per delivery sequence; model vectors, not byte-compat claims against any
  other tool). Delay or a gap cannot change either an event outcome or the
  composed history, and each schedule's applied root sequence is a prefix of the
  single canonical slot-ordered history.
* **B4 — authority surface.** The resolved object contains only
  `{event_hash, outcome, source_root?}`; no successor key, delegate, membership
  edit, recovery authority, or permission field.
* **N1 — authorization never flavors the pulse.** The proof recovered from *any*
  `>= t` valid share subset equals the resolver's boundary-admitted proof: a
  CONFIRM certificate, witness, or packet path answers only *"may this member
  emit a share yet?"* and never enters `P_s` or `R_s`.
* **N3 — genuine threshold theorem.** `ThresholdAuthority` keeps a member roster
  with per-member shares: `t-1` valid shares recover **no** proof; every one of
  the `C(n,t)` distinct valid `t`-subsets (and `t+1`, and full) for the *same*
  close recovers the **byte-identical** canonical `P_s`; duplicate members,
  out-of-roster members, and shares for a *different* close are rejected. The
  same check asserts **ledger-realistic applied history**: under every delivery
  schedule the *applied* root sequence is a prefix of the canonical
  slot-ordered history — nodes cache future proofs but their applied view stalls
  at the first gap, so nodes differ only in prefix length and never exhibit an
  applied `ROOT,UNKNOWN,ROOT` hole.
* **N5 — predecessor-state activation.** The epoch applied for a slot is a pure
  function of the *predecessor canonical state* (the ledger that externalized
  the predecessor), never local quorum sets or membership bookkeeping — so
  activation is deterministic, replay-safe, and cannot be steered after the fact.

The same model asserts the three exit laws (O1–O3 above), the compositional law
`|H_n| = 1` across duplicate/replay/reorder paths, the three kill questions
(K1–K3), the three source properties (S1–S3), the **genuine threshold theorem**
(N1/N3), **ledger-realistic applied-prefix** history (Noot #3), and
**predecessor-state activation** (Noot #5), all deterministic and repinned. The
B3 digests (one per per-event delivery sequence) are intentionally stated here so
an independent implementation that reproduces the state machine must match them
(a drift in the close-input / close-lock / challenge / transition encoding
changes the digests).

### Implementations sit behind the interface

`RandomnessEpoch` is the normative interface. "drand-compatible threshold BLS",
"future Stellar-native DKG/threshold beacon", or a verifiable-delayed beacon are
implementations behind it. Layer A's ECVRF work remains independently useful
without being asked to prove subset neutrality it cannot provide; if Stellar
later lands a DKG/threshold group, the group key becomes the consumer-facing
authority and the member roster is setup/recovery machinery committed by the
epoch — not an input to each consumer draw.

### Native seam and the `LedgerHeader` proof path for catchup

The minimal native boundary handed to Core/Rust reviewers is:

```text
Core:
  canonical close input -> C_s
  exact-close authorization -> may_release_share
Rust:
  share_produce / share_verify
  proof_recover(any valid >=t subset) -> canonical P_s
  proof_verify_and_root(epoch, C_s, P_s) -> R_s
LedgerHeader.ext:
  canonical P_s (+ epoch selector if not otherwise derivable)
```

The canonical proof is **persisted in the closed ledger** — a `LedgerHeader`
extension `{epoch_hash, canonical_proof}` — not inside the SCP value. This is
not circular for catchup: `LedgerHeaderHistoryEntry` carries that header into
history/catchup, a catchup node reads the expected entry before replaying that
ledger, validates the predecessor and txset, and *then* builds `LedgerCloseData`.
Live threshold transport and the archived header proof therefore feed the same
`proof_verify_and_root` verifier before apply; the root stays **derived**, never
stored. The `LedgerHeader` extension also cryptographically binds the proof to
the exact ledger hash, so replay self-contains the proof without carrying
post-lock evidence in the consensus value.

### Status and the Layer A / Layer B deployment fork

The epoch-authority interface and the one-future law (single + compositional)
are the stated acceptance bar for protocol randomness. The underlying
subset-invariant/reconstruction primitive is **not yet in Stellar's reviewed
crypto pipeline**, so Layer B stays `Draft` and the conformance vectors pin the
invariant (not a fabricated construction). This matches the agreed review
direction: change the claim when the invariant disproves the mechanism rather
than defend the mechanism.

**Deployment fork (from review).** This CAP now separates *deployment* from
*evidence*:

* **Layer A + the `ECVRF-EDWARDS25519-SHA512-TAI` primitive (PR #5409):**
  independently useful ECVRF primitive plus this CAP's research and conformance
  evidence showing exactly where a per-reveal aggregate's boundary lies (seven
  distinct roots for one `Q=6/t=5` commit set — Layer A is bounded but
  **not** subset-invariant). It is kept as evidence and as a first-class
  primitive, **not** pitched as the final protocol-randomness authority.
* **Protocol deployment: gated on the Layer B one-future construction.** The
  normative protocol-randomness path waits for the one-future primitive, then
  freezes one runtime-decodable wire format around the `RandomnessEpoch`
  interface and wires consumers once against the final interface.

Adopting this fork removes upstream protocol risk that shipping a
consensus-visible Layer-A commit/reveal/fallback format would otherwise carry:
candidate-authored `Q`, observation-dependent reveal inclusion, the LCL
fallback choice, a second migration, and (potentially) the trailing-field XDR
problem all stop being things Stellar has to ship merely to reach the
architecture it actually wants. The XDR in this CAP is retained as the
conformance/evidence surface and as the reference for what a
runtime-decodable, backward-decode-gated extension must look like; whether it
advances to a frozen protocol format is decided by the Working Group together
with the one-future primitive choice.

## Exit Criteria

The verifiable conditions that must be met before this CAP moves to
`Implemented` and can be included in a protocol release:

- [ ] The `ECVRF-EDWARDS25519-SHA512-TAI` primitive (PR #5409) is merged and the
      RFC 9381 vectors pass in the core build.
- [ ] **Single deployment path (no intermediate Layer-A wire format).** The
      trailing Layer-A `StellarValue` fields (`VRFCommit`/`VRFReveal` and
      `vrfCommits`/`vrfReveals`/`vrfBeaconNext`, gated on `VRF_RANDOMNESS`) are
      **not frozen as a shipping format** — they remain the conformance/evidence
      surface. The protocol-randomness wire format that ships is the single
      runtime-decodable representation around the Layer-B `RandomnessEpoch`
      interface, frozen and accepted by the protocol working group once the
      one-future primitive is chosen.
- [ ] **Backward-decode gate (hard review gate).** The randomness representation
      is decidable at runtime, not only at compile time: a **backward-decode
      conformance test** decodes a legacy-format `StellarValue` under the new
      schema and a new value under a legacy-only schema, with each specified to
      succeed or fail — never silently mis-read. The gate validates **only** the
      runtime-discriminated Layer-B representation; the evidence-only `#ifdef`
      trailing members (Section "Status and the Layer A / Layer B deployment
      fork") are explicitly **not** a candidate shipping shape, so this sentence
      does not leave them as a possible final form — the final shape is the single
      wire-discriminated Layer-B arm.
- [ ] Adversarial conformance vectors V1–V8 (Section "Test Cases") are
      implemented and passing in a deterministic test harness, including the
      fixed transcript fixtures in `contents/cap-0089`; these are carried as
      **evidence cross-checked by native Core/Rust conformance** — the external
      harnesses describe the boundary but cannot define protocol truth.
- [ ] The three labeled consumers of the one externalized-close root `R_s`
      (`sorobanBasePrngSeed = KDF(R_s, "PRNG")`,
      apply order `SHA-256(KDF(R_s, "APPLY") ‖ txHash)`, and next-ledger
      nomination `KDF(R_s, "NOMINATION")`) each pass a round-trip
      determinism test across multiple nodes, and a proposer sweep over candidate
      externalized values for a slot cannot move the root that any consumer seals
      against.
- [ ] The feature has been exercised on a test network with Horizon and RPC up
      and reflecting the change, and `LedgerCloseMeta`s captured from new tests
      pass downstream ingestion test cases.
- [ ] V1 (prior-ledger grinding), V2 (single-contribution withholding), and V8
      (transcript/beacon mutation) demonstrably fail closed on a native
      Core/Rust consensus run, not only in external unit tests.
- [ ] **Layer B (protocol randomness) one-future-neutrality gate.** The
      subset-invariant exit criterion is *not* met by Layer A's per-reveal
      aggregate and is deliberately kept in `Draft` until a precommitted
      **randomness epoch** (fixed group key, Sybil-resistant membership
      commitment, threshold, activation ledger) with a reconstructable scheduled
      output lands as a reviewed primitive. Exit evidence for that gate:
      every closed ledger yields a single canonical close `C_s`, a single
      challenge, a single proof, and a single root `R_s` (or **UNKNOWN**/stalled
      apply), with **no caller-selected `outcome_class` and no `NO_PULSE`**,
      swept across reveal subsets,
      identity splitting at constant influence, transport schedules, consumer
      lock timing, consensus-path variation, and migration — a close below
      threshold being **UNKNOWN** (observer-relative,
      never an alternate entropy source and never a timeout-derived no-pulse).
      Because per-round
      bounded choice compounds, the gate also asserts the **compositional** law
      on a long randomized run — randomized machine speeds,
      routing/duplication/withholding, replay, recovery, and implementation
      order — that every run yields the **identical authoritative history
      digest** (`H_n` with `|H_n| = 1` for every prefix `n`) or stalls
      deterministically on the same UNKNOWN boundary; see "Layer B: Randomness
      Epoch". The
      executable `layer_b_model.py` (B1 single-pulse/no-class binding, B2 exact
      externalized-value challenge, B3 601-close transport/replay composition
      with a
      pinned digest, B4 authority surface) plus exit laws O1–O3 and the three
      kill questions are the interface tests for whichever reconstruction
      primitive is evaluated next.
- [ ] **Spec parity.** CAP prose, XDR, fixtures, and checker describe the same
      membership rule, threshold/failure rule, purpose bytes, and acceptance
      state; any disagreement between the four surfaces fails conformance.
- [ ] **Genuine threshold theorem + applied-prefix + predecessor-activation
      gates (Layer B model).** The native `proof_recover(any valid >= t subset)`
      must recover the **byte-identical** canonical `P_s` for the same close (no
      subset flavors the proof), reject `t-1` subsets, duplicate/out-of-roster
      members, and shares for a different close (`layer_b_model.py` N1/N3); the
      *applied* root history must remain a prefix of the canonical slot-ordered
      history under all delivery schedules (Noot #3, no applied
      `ROOT,UNKNOWN,ROOT` holes); and epoch activation must be a pure function of
      the **predecessor canonical state**, never local quorum sets (Noot #5).
- [ ] **`LedgerHeader` proof path for catchup.** The canonical `P_s` is persisted
      in a `LedgerHeader` extension `{epoch_hash, canonical_proof}` and
      re-verified from `LedgerHeaderHistoryEntry` during catchup before the ledger
      is applied; root stays derived (`proof_verify_and_root`) and replay is
      self-contained without post-lock evidence in the SCP value (Noot #4).
- [ ] **Layer-B resource accounting (acceptance target).** Once the one-future
      primitive is selected, Core/Rust benchmarks MUST quantify Layer-B compute
      (threshold reconstruction + share/proof verification + one `SHA-256` KDF
      per labelled consumer per slot), bandwidth, storage, and added close
      latency against SCP round time — as an acceptance target, not assumed away.

The author is an independent contributor. The cryptographic primitive and this
protocol design were developed in the open (issue #4388 → PR #5409 → this CAP)

A second design-level correction from review is explicit in this revision: a
per-reveal hash aggregate cannot be **subset-invariant** — a changed valid
reveal subset changes the hash — so Layer A of this CAP (the per-reveal

explicitly **not** claimed to reach one-future neutrality. Subset-invariant
protocol randomness (Layer B) is scoped as a separate, `Draft` target gated on
a precommitted randomness-epoch/reconstruction primitive, with consumer sealing
collapsed to a **single pulse per closed ledger**: one close `C_s`, one
challenge, one root `R_s`, and three labeled consumers of that one root
